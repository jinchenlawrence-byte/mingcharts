# 三、❌ 第三处入口漏洞：地理 `/geo` 未接时区

## 3.1 问题

我扫了全部会排盘的入口，发现 `src/app/api/geo/route.ts:38`：

```ts
// 排盘 → 旺衰（地理分析的喜忌基准）
const chart = paipan({ year, month, day, hour, minute, gender })   // ← 没传 birthLng / birthZone
```

**同一个 route 里，`body.birthplace` 被用来算「相对方位」（第 42–48 行），
却没用来算「真太阳时校正」。**

`src/app/geo/page.tsx` 的 `formData` 也只有 `birthplace`，**没有 `birthLng` / `birthZone`**。

## 3.2 影响量化（我实测）

**关键：不是"必然错"，而是"约一半情况下错"。**

以纽约（偏移 −56 分）为例，时辰每 2 小时一换：

```
出生时刻   geo(偏移0)   正确(−56)   是否变化
13:10      丁未         丙午        ★ 变了
13:30      丁未         丙午        ★ 变了
11:30      丙午         乙巳        ★ 变了
14:00      丁未         丁未        不变
14:30      丁未         丁未        不变
12:30      丙午         丙午        不变
```

**规律**：偏移 56 分时，出生时刻落在**每个时辰的前 56 分钟**内 → 校正后跨过边界 → 时柱改变。

**即约 56/120 ≈ 47% 的北美出生时刻，geo 模块会用错时柱** → 旺衰可能错 → 喜用可能错 → **城市推荐可能错**。

## 3.3 而且这是个**既存**问题，中国用户也受影响

```
乌鲁木齐 1990-01-15 14:30
  geo 路径（偏移 0）   → 时柱 癸未
  正确路径（偏移 -130）→ 时柱 壬午    ★ 变了
```

**偏移 −130 分 > 120 分（一个完整时辰）→ 时柱必然改变。**
所以**新疆、西藏等西部城市的用户在 geo 模块里一直用的是错时柱** ——
这是本轮之前就存在的问题，北美化只是让它更显眼。

## 3.4 修法

1. `api/geo/route.ts`：接收 `birthLng` / `birthZone`，传给 `paipan()`
2. `geo/page.tsx`：接入共用模块 `birthCities.ts`（复用批命页那套城市分组下拉＋手动经度＋时区提示）
3. **加一条回归**：同一出生数据，**geo 路径与批命路径的四柱必须一致**

> **第 3 条是关键** —— 它把"入口间一致性"变成可自动检查的断言，
> 避免以后再出现"某个入口忘了接"。

## 3.5 顺带说明

`src/app/bazi/[year]/[month]/[day]/page.tsx:33` 也调 `paipan()` 且不传时区，
**但那个页面明写「默认12:00，日详情页无精确时辰」，属合法的无校正场景** —— 不是漏洞 ✓

# 四、一处潜在脆弱性（我实测**未复现**，故列为加固建议）

`toTrueSolarTime` 用**本地 getter** 构造与读取：

```ts
const d = new Date(year, month - 1, day, hour, minute, 0)   // 本地
const a = new Date(d.getTime() + offsetMin * 60000)
return { year: a.getFullYear(), ... a.getHours() ... }       // 本地
```

**理论风险**：若**服务器本地时区本身有夏令时**，且平移恰好跨越该时区的 DST 切换点，
读回的钟表时间会差 1 小时。

**我实测（用子进程预设 TZ）**：

```
TZ=UTC               → 与手工 UTC 核算完全一致
TZ=America/New_York  → 与手工 UTC 核算完全一致（未复现偏差）
```

**→ 未复现，不是现实缺陷。** 生产环境通常是 UTC（无 DST），本就安全。

**建议**（可选加固）：改用 UTC 构造与读取（`Date.UTC` + `getUTC*`），
使实现**不依赖服务器时区** —— 消除这类隐患，代价极小。
