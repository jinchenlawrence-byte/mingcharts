# 一、四项确定性小改

## 1.1 `tsx` 未入依赖（P2）

**现状**：

```json
"verify": "npx tsx scripts/test-geo-accept.mjs && npx tsx scripts/test-wealth-accept.mjs && npx tsx scripts/test-regression.mjs"
```

`tsx` **既不在 `dependencies` 也不在 `devDependencies`**。
本机因 npx 缓存能跑，但**新环境 / CI 上会临时下载**（慢，离线则失败）。

**改法**：

```json
"devDependencies": { "tsx": "^4.19.0" },
"scripts": {
  "verify": "tsx scripts/test-geo-accept.mjs && tsx scripts/test-wealth-accept.mjs && tsx scripts/test-regression.mjs"
}
```

**并建议**：把 `tsc --noEmit` 也纳入 `verify`（它是"验证三件套"的第一件，现在没串进去）：

```json
"verify": "tsc --noEmit && tsx scripts/test-geo-accept.mjs && ..."
```

## 1.2 文档化「84°/24° + 门控卦位分离」（P2）

**背景**：复核已裁决 Q1（**保持 84°**）与 Q3（**需要文档化**）。理由：

- 土 24° 明显窄于其余四类 84°，**这是刻意的**（土在传统中为「中央」，本非方位）
- 卦位（8 等分，传统八卦）与门控（5 类）**划分标准不同** →
  同一城市可能「卦位属土、门控属木」，**这不是 bug**

**改法**：在 `geo.ts` 头部注释 + `references`（或项目文档）写清：

```
方位体系说明（避免后续被当成 bug 提回）：
· 卦位（8 等分，各 45°）：传统八卦，用于【方位标签】（如"东南·巽木"）
· 门控（5 类，四正各 84°、四维各 6°）：用于【五行判定】，服务"每类候选可取满"
· 两者标准不同 → 同一城市可能「卦位属土、门控属木」，属刻意设计
· 土仅 24°：因土在传统中为「中央」而非方位，故只保留四维过渡带
```

> 总纲已同步写入 **§8.4.4「标签与判据分离时，必须显式说明二者关系」**，可直接引用。

# 二、★ AI 输出合规抽验（本轮重点）

## 2.1 为什么必须做

前几轮改了 **4 个 AI 模块**的 prompt：

| 模块 | 行数 | 前几轮加入的约束 |
|---|---|---|
| `aiAnalysis.ts` | 257 | 大运段禁绝对标签、须分维度+结构病、须带免责立场 |
| `aiHemun.ts` | 151 | 依据分级须体现、不得把民俗/产品设定说成典籍 |
| `aiGeo.ts` | 185 | 城市五行取象须声明为产品设定 |
| `aiZiwei.ts` | 183 | （同族约束） |

**但全部只做了 prompt 改写，没跑过一次真实调用。**

> **prompt 写对了，不等于模型照做。** 这是本轮唯一有实质风险的项——
> 如果模型输出仍出现"大吉"，那前面几轮在规则引擎上的努力就被 AI 层泄掉了。

## 2.2 抽验方式（成本可控）

**用现有测试脚手架**（`paipan` + `generateAnalysis`）跑真实调用，**每个模块 1 个命例**即可。

```
① 回归用例（辛未 壬辰 壬子 壬寅 男，1991-04-12 03:10）
   → 调 aiAnalysis（批命）
② 合婚测试对（男 1990-5-8 16:30 / 女 1992-8-15 9:00）
   → 调 aiHemun
③ 出生地广州
   → 调 aiGeo
```

**成本**：4 次调用，按 deepseek-chat 计 **远低于 ¥1**。

**API 配置已确认可用**（我实测过 `.env.local` 里的 key，两个 endpoint 均 HTTP 200）。
**若担心成本，先只跑 ①（批命），它承载的约束最多。**

## 2.3 检查项（逐条打钩）

对每段 AI 输出做**程序化检查**（不是人工看）：

| # | 检查 | 判据 | 期望 |
|---|---|---|---|
| 1 | **禁用词** | 文本含 `大吉｜大凶｜积极进取｜突破性进展｜必｜一定｜注定` | **0 命中** |
| 2 | **免责立场** | 含 `倾向｜参考｜宜｜注意` 之一，且含 `非确定性｜仅供参考｜不构成` 之一 | ✓ |
| 3 | **依据分级**（合婚/地理） | 含至少两类依据词（`典籍｜古法｜民俗｜产品设定`） | ✓ |
| 4 | **不得混淆依据** | 不得出现「典籍」与「生肖/纳音/大运同步」同句并列宣称 | ✓ |
| 5 | **分维度**（批命大运段） | 含 `事业｜财运｜健康｜六亲` 中至少 3 个 | ✓ |
| 6 | **结构病**（批命大运段） | 含 `被合｜被冲｜被化｜被夺｜深藏｜孤立｜印化｜比劫` 至少 1 个 | ✓ |
| 7 | **不编造** | 输出的干支/十神/大运，须能在算法给定的事实集里找到 | ✓ |

**建议**：把 1–7 写成一个可复用脚本 `scripts/test-ai-compliance.mjs`，
纳入 `npm run verify`（或单独 `npm run verify:ai`，因为它需要网络 + 消耗额度）。

## 2.4 若不合规怎么办

按"**先改 prompt，再考虑加后置过滤**"的顺序：

| 情况 | 处理 |
|---|---|
| 仅禁用词命中 | 改 prompt 强化禁用词列表；**若仍命中，加一层输出后置替换/拦截** |
| 分维度/结构病缺失 | 改 prompt 的 requirement 描述，给出更明确的格式要求（如"必须以 事业【】财运【】健康【】六亲【】 四项分别成句"） |
| 编造干支 | **红线 1**：必须改 prompt 并在后置加**校验**（对照算法事实集） |
| 免责缺失 | prompt 的 `SYSTEM_PROMPT` 末尾强制一段固定免责文案 |

> ⚠️ **不要用后置过滤代替 prompt 修正。** 过滤是兜底，不是主手段——
> 否则模型会持续生成违规内容，只是被掩盖掉。

## 2.5 必须避免

- ❌ **不得**为了"测试通过"而把检查项放宽
- ❌ **不得**只人工"看一眼觉得没问题"就报通过 —— **要留程序化输出**
- ✅ 若发现不合规，**如实报出**（这正是本轮的目的）

# 三、附带发现：endpoint 拼接不一致（低优先）

四个模块的 URL 拼接方式不同：

| 模块 | 拼接 |
|---|---|
| `aiAnalysis.ts` | `${AI_BASE_URL}/v1/chat/completions` |
| `aiHemun.ts` | `${AI_BASE_URL}/v1/chat/completions` |
| **`aiGeo.ts`** | `${AI_BASE_URL}/chat/completions` ← 无 `/v1` |
| **`aiZiwei.ts`** | `${AI_BASE_URL}/chat/completions` ← 无 `/v1` |

**我已实测**：`https://api.deepseek.com/chat/completions` 与
`.../v1/chat/completions` **都返回 HTTP 200**（DeepSeek 兼容两种）。

**所以这不是 bug，当前不会出错。** 但建议统一（抽一个共享的 `aiClient.ts`），
原因：**若将来换供应商（只接受其中一种形式），这 4 个模块会有一半静默失败。**

> **§一 是收尾，照做即可。§二 才是本轮的价值所在。**
