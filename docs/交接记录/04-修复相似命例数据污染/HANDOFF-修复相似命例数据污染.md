## P0-2 去重改为「按质量等级取优」

### 现象
`line 72` 现在是：
```js
if (c.person && (!existing.person || c.text.length > existing.text.length)) {
  seen.set(key, c)
}
```
**「文本更长」不等于「更对」。** 实例（阎锡山）：

```
用户库展示: 癸未 辛酉 乙酉 丁亥 | 阎锡山
  text = '，辛金透，丁火刚，秋木盛，三者皆备，极等之贵，以其有力也。
          官强财透，身逢禄刃，如丙生子月，癸水透，庚金露，而坐寅午…'
```

两个问题：**① 以「，」开头（截断残片）；② 后半段举的是「丙生子月」——与阎锡山（乙木日主）无关，
是把书里下一段泛论并进来了。**

而同一命例在 `cases-zp-llm.jsonl` / `cases-gist-llm.jsonl` 里是干净的：
```
'辛金透，丁火刚，秋木盛，三者皆备，极等之贵，以其有力也'
```
**坏记录因文本更长，覆盖了干净版本。**

> 所以「阎锡山命盘精确命中」这个说法**只对了一半：四柱对，断语错**。

### 修复
改为**按文件质量等级取优**：

```js
// 文件质量等级从 index.json 读；A > B > C
const gradeRank = { A: 3, B: 2, C: 1 }
const rank = (c) => (gradeRank[c._grade] || 0) * 10 + (c.person ? 1 : 0)

// 只有更优才替换；同级再比人物、最后才比长度
const better =
  rank(c) > rank(existing) ||
  (rank(c) === rank(existing) && c.person && !existing.person) ||
  (rank(c) === rank(existing) && !!c.person === !!existing.person &&
   c.text.length > existing.text.length)

if (better) seen.set(key, c)
```

**关键**：质量等级是第一优先，文本长度降为**最后**的平手判据。

# 三、【P1】两项数据质量

## P1-1 加文本质量门槛（87 条短/残断语）

```
壬午癸丑丁卯丙午 | '用 之命。'      ← 截断
乙巳丁亥己丑甲子 | '于大学士。'      ← 截断
己丑丁丑己巳丁卯 | '丁透丙藏'        ← 是术语，不是断语
庚辰丁亥庚子庚辰 | '丁火煅金'        ← 同上
```

在 `extractCase()` 里加：

```js
// 文本太短 → 剔除
if (text.length < 8) return null

// 残句特征 → 剔除
if (/^[，。、；：]/.test(text)) return null        // 以标点开头
if (/(之命。|于大学士。)$/.test(text) && text.length < 12) return null  // 明显截断
```

**注意**：`'尚书'` `'知府'` `'位至府尹。'` 这类**是合格的断语**（古人批语本就简短），
**不要一刀切删掉**。判据是"是否截断/残缺"，不是"是否够长"。

**建议**：把长度门槛定在 **6–8 字**，并对 <12 字者做人工抽检后再定。

## P1-2 `person` 字段加噪声过滤

抽查发现这些"人名"是解析产物：

```
'孝廉'  '茂才'  '盖庚丁两'  '相文敏'  '陆商阎'  '傅后庵公'
```

- `孝廉`/`茂才` = **功名**，不是人名
- `盖庚丁两` = "盖庚丁两透…"的**截断**
- `陆商阎`/`相文敏` = 疑似**跨句拼接**

**修复**：加黑名单/校验

```js
const NOT_A_NAME = /^(孝廉|茂才|进士|举人|解元|状元|贡士|生员|秀才|明经|及第)$/
const BAD_PATTERN = /^(盖|如|若|夫|且|然|故|此|其|凡|按|又|或)/

if (person && (NOT_A_NAME.test(person) || BAD_PATTERN.test(person) || person.length > 4)) {
  person = null   // 宁可不显示，也不显示错的
}
```

> **原则**：前端展示"人物：孝廉"会显得很业余。**宁可留空。**

# 四、【P2】两个模块的口径问题

## P2-1 合婚：评分口径偏松

`src/lib/hemun.ts:160`
```js
let score = 60        // 基础分
...
const grade = totalScore >= 85 ? '上等良缘' : ...
```

**问题**：
- 七维度**全部中性**也得 **60 分**（落在"中等婚配"）
- 到"下等"须净亏 5 分以上
- 有效区间被压在 **55–100**，"上等"很容易拿到（实测样本直接 86 分）

**有"讨好用户"的观感。** 而命理合婚本无"打分"传统，**给精确到个位的分数反而显得不可信**。

**修复（二选一）**：
- **A**：基础分降到 **45**，并拉大各维度 delta 的区分度
- **B（推荐）**：保留计算但**弱化单一分数**——改为**七个维度分项结论** + 一句总评，
  不突出"86 分"这种伪精确数字

## P2-2 地理：城市五行混用两套不相容依据

`src/data/geo-cities.json` 抽查：

```
北京   wx=土  reason="古都皇城居中原之北，厚土载物；政金肃敛"
大连   wx=水  reason="黄渤海良港，航运造船属水"
太原   wx=金  reason="煤铁之乡、能源重工，盆地土生金"
长春   wx=木  reason="森林城、汽车城，黑土地上木气生发"
```

**两个问题**：

**① 混用两套互不相容的体系**

| 体系 | 依据 | 北京应判 |
|---|---|---|
| **方位五行**（命理正统） | 东木/南火/西金/**北水**/中土 | **水** |
| **物产/产业取象**（现代发明） | 皇城=土、煤铁=金、港口=水 | **土** ← 实际用了这个 |

大连按"在北"和"港口"都判水（自洽），**北京按方位该是水却判了土** —— 标准不一致。

**② `reason` 里没有一条引古籍** —— "厚土载物""政金肃敛"是现代推演。

而 `wx` 直接参与打分（"城市主气合目标 +28"），**等于把现代发明包装成命理结论卖给用户**。

**修复**：
1. **统一标准**：优先用**方位五行**（唯一有命理传统的：东方木/南方火/西方金/北方水/中央土）；
   物产取象降为**次要**参考
2. **页面明确声明**：`geo/page.tsx` 与 `aiGeo.ts` 里加一句
   **"城市五行取象为本产品设定，非古籍原文依据"**
3. 若坚持物产取象，则**必须**标注为自创体系

> 这跟我们做命例库时反复强调的是同一个道理：
> **自己推演出来的东西，必须标明是自己推演的，不能冒充古籍。**
