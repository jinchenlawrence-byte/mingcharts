# P0 缺陷报告：会员权益与单次报告冲突（＋ 连带查出两处）

> **发现者**：用户（2026-10-07）
> **复核者**：DeepSeek 侧
> **性质**：**商业逻辑缺陷** —— 不是代码写错，是**实现与已批准的设计不一致**
> **严重度**：**P0** —— 若照此上线，**单次报告 SKU 一个都卖不出去**，且**付费墙形同虚设**
> **用户的观察**：「单次解读 $29.9，月度会员 $9.9 且不限次数解读 → 根本没人买单次产品了」

---

# 一、用户是对的，而且比"单次卖不出去"更严重

## 1.1 现状（我方逐处核实）

| 位置 | 内容 |
|---|---|
| `pricing.ts:64` | `member_monthly.desc = '按月订阅，深度报告不限次数'` |
| `pricing/page.tsx:75` | 会员卡 `desc = '重度用户更划算，命书不限次数'` |
| `pricing/page.tsx:79` | 权益列表 `'本账号命书报告不限次数'` |
| `pricing/page.tsx:99-100` | **FAQ：**「会员期内命书不限次数是什么意思？」<br>→「开通会员后，会员期内你账号下的**所有命盘都可以免费解锁完整命书**，不用每次 **$29.99** 单独购买」 |
| `pricing/page.tsx:222` | 对比表 `['不限次数', false, false, true]` |
| `entitlement.ts:34` | `canView`: `return ent.member \|\| …` —— **会员放行一切** |
| `unlock/route.ts:22` | `// 会员期内免单次解锁费用（命书不限次数）` |

**→ 不是"文案写错了"**：**权益判定（`canView`）本身就是"会员全放行"** ✓
**文案与实现是一致的，一致地偏离了设计。**

## 1.2 经济学：单次 SKU 是**死的**

```
命书单次        $29.99
月度会员        $9.90   →  深度报告【不限次数】

用户算一下：
  买 1 份命书                 = $29.99
  开 1 个月会员（无限份命书）  = $9.90      ← 更便宜，还无限
→ 【买 1 份都不如开会员】
```

**所以不是"没人买"，是"买它的人算错账才会买"** ✓

## 1.3 ★ 连带后果（用户没提到的部分）

**① 整个报告 SKU 结构变成装饰**

```
$29.99 命书 / $19.99 年运 / $29.99 合婚 / $24.99 紫微 / $19.99 地理 / $59.99 套餐
      ↓  在 $9.9/月「不限次数」面前
全部作废 —— 用户开一个月会员就把这些全解锁了
```

**② 年会员 $49 也失去意义**

```
月会员 $9.90 × 12 = $118.80      vs      年会员 $49
用户直接开年会员 → 一年内所有报告无限
→ 客单价被压到 $49 封顶，价格表上那 6 个 SKU 一个都不会被购买
```

**③ 付费墙在结构上无法成立**

**产品变成「$49/年，全部解锁」** —— 而这不是设计意图。

# 二、根因：实现偏离了**已批准的设计**

## 2.1 设计稿是怎么说的

`docs/定价方案.md` §4.2（**用户已批准**）：

```
报告（$19.99–$34.99）  → 单独买，高单价，一次性
订阅（$49/年）          → 只卖【高频】：个性化日运（每日）＋ 流月更新
                          ★【不含报告】
```

**§2.2 还专门论证过**：FateTell 的核心设计就是
**「报告卖深度（$39.99，一次性），订阅卖高频（$59.99/年），两条线互不侵蚀」** ✓

## 2.2 为什么实现会跑偏

```
原版 App 的¥29.9/月会员 = 「所有命盘免费解锁」
      ↓  改价时
把旧会员的【权益文案】照搬，只把价格换成 $9.90
      ↓
但设计稿已经把订阅的【权益】改成「日运＋流月，不含报告」
      ↓
★ 权益没有被数据化，只存在于中文描述里 → 没人发现它跑偏了
```

## 2.3 ★ 根本原因：**权益从未被数据化，断言也只盖了价格**

```ts
// pricing.ts 现状：只有价格，没有权益
export interface Sku {
  id: SkuId
  name: string
  desc: string          // ← 权益只在【中文描述】里
  priceUSD: number      // ← 只有价格是结构化的
  kind: SkuKind
  durationDays?: number
  includes?: SkuId[]    // 只有 bundle3 用了
}
```

**而我的任务书 §1.2 里写过一个 `grants: GrantRule[]`** ——
**实现时被略过了，而我的验收标准（§1.6）也没有任何一条断言权益** ✗

**`test-pricing-accept.mjs` 断言了 9 个价格，一个权益都没断言** ✓
→ **所以价格一分不差、权益完全跑偏，`verify` 全绿。**

> **★ 这条教训我方责任最大（见 §五）**：
> **规格里凡有"数字 ＋ 语义"两部分，断言不能只盖数字。**
> **数字是外壳，语义才是产品真正卖什么。**

# 三、连带查出第二处：支付流水金额仍是旧价

```ts
// src/app/api/unlock/route.ts
74: // 记录支付流水（会员免单，非会员按 pricing.ts 的 fatebook 价。MVP模拟，接入真实支付时替换）
75: if (!isMember) {
79:     amount: 19.9,        // ★ 仍是 ¥19.9，而命书是 $29.99
```

**注释说"按 pricing.ts 的 fatebook 价"，代码却硬编码 `19.9`** —— **注释与代码互相矛盾** ✓

**为什么要紧**：这是**支付流水的金额**。接真实支付后，
**账上记 $19.9、实际收 $29.99** → 对账必然出问题。

**★ 为什么我上轮的价格扫尾没抓到它**：

```
我的判据是 /¥\s*\d/ —— 查的是「带人民币符号的文案」
而这里是【裸数字】amount: 19.9 —— 没有 ¥ 符号
→ 判据只盖了一种形态，漏了另一种
```

**价目漂移有两种形态**：**文案里的「¥19.9」** 与 **代码里的 `amount: 19.9`**。
**我的断言只盖了前者** ✗

# 四、修法

## 4.1 ★ 权益数据化（依 §8.5.1：单一事实源）

```ts
// pricing.ts —— 把"买到什么"变成数据，而不是文案
export interface Sku {
  id: SkuId
  name: string
  desc: string
  priceUSD: number
  kind: SkuKind
  durationDays?: number
  /** ★ 购买本 SKU 后，可查看哪些内容 */
  grants: SkuId[] | 'all'       // 'all' 只应出现在显式的"全站套餐"
}

// 按已批准的设计（docs/定价方案.md §4.2）：
fatebook:       { grants: ['fatebook'] }
annual_report:  { grants: ['annual_report'] }
hemun:          { grants: ['hemun'] }
ziwei_deep:     { grants: ['ziwei_deep'] }
geo:            { grants: ['geo'] }
bundle3:        { grants: ['fatebook', 'ziwei_deep', 'geo'] }
member_monthly: { grants: ['daily', 'liuyue'] }   // ★ 不含任何报告 SKU
member_yearly:  { grants: ['daily', 'liuyue'] }   // ★ 同上
```

**★ 需要一个新 SKU `daily`/`liuyue` 表示订阅型内容** —— 否则"会员权益"无处可挂。

## 4.2 `canView` 改为查 grants，而不是「会员全放行」

```ts
export function canView(ent: Entitlements, sku: SkuId): boolean {
  if (!ENTITLEMENT_ENFORCE) return true
  // 已购单项：自身 or 任何 grants 覆盖 sku 的 SKU
  // 会员：其 grants 也必须覆盖 sku 才放行 —— ★ 不再无条件放行
}
```

**⚠️ 关键**：`ent.member` **不再是万能通行证**。会员的权益由**其 SKU 的 grants** 决定 ✓

## 4.3 清理全部用户可见文案

| 文件 | 要改 |
|---|---|
| `pricing.ts:64` | `desc` 改为真实权益（日运＋流月，不含报告） |
| `pricing.ts:69` | 年会员 desc 同上 |
| `pricing/page.tsx:75/79/99-100/222` | 会员卡、FAQ、对比表全部改 |
| `unlock/route.ts:22` | 注释改为「会员不解除命书锁定（订阅不含报告）」 |
| `unlock/route.ts:79` | **`amount: 19.9` → 取 `SKUS.fatebook.priceUSD`** |

## 4.4 ★ 断言要同时盖住「价格」与「权益」

**扩 `test-pricing-accept.mjs`**：

```
① 价格表（已有 9 项）—— 保留
② ★ 权益表断言（新增）：
     - 每个 SKU 的 grants 与拍板表逐项一致
     - ★ 专项断言：member_monthly / member_yearly 的 grants
       【不含任何报告 SKU】（fatebook/annual_report/hemun/ziwei_deep/geo/bundle3）
     - bundle3 的 grants 恰为 fatebook+ziwei_deep+geo
③ ★ 裸数字金额扫描（新增）：
     - 扫描 src 下形如 `amount:\s*\d` / `price:\s*\d` 的字面量，应为 0 命中
     - （我上轮只扫了带 ¥ 的文案，漏了裸数字 —— 见 §三）
④ 牙口：把任一 grants 改回"含全部报告" → 必须翻红
```

## 4.5 ⚠️ 但**菜单现在没有"货"**（排期问题）

**订阅的真实价值是「日运（每日）＋ 流月更新」—— 而这两样 Part B 还在做（`daily.ts` 只到流日引擎）。**

**所以**：

```
在日运功能上线前，【不要对外销售会员】——
否则用户付费买到的是"什么都没有"。
```

**好消息**：真实支付是第 6–7 步，尚未接入 ✓ **现在没人能买** ✓ **有时间**。

**建议排期**：

```
1. 修权益模型（本报告 §4.1–4.4）        ← 立刻，纯代码
2. 日运上线（Part B 主线）              ← 订阅才有货
3. 再把会员放上价格页                   ← 有货才卖
```
