# 四、Q1 / Q2 / Q3 裁决

## Q1：门控宽度 84°（土 24°）还是回调等宽 72°？

**裁决：保持 84°。**

理由：

1. **操作判据全过** —— 土最低 25 个候选（拉萨），远超 Top6。**没有功能性问题。**
2. **土在传统中是「中央」，本非方位** —— 给它窄扇区（仅四维过渡带），比把它拉宽到与其他四类等宽**更贴近这一性质**。
   等宽 72° 会让"土"看起来像第五个方位，反而不准。
3. **上海木缺口在两种方案下都存在** —— 84° 时木=4、72° 时木=3，**都取不满**。
   所以这个选择**不影响**上海的处理路径，明示 notice 无论如何都需要。
4. **可逆** —— 若后续发现土类推荐质量偏弱（扇区窄、可选城少导致同质化），再回调 72° 即可。
   **但要求**：把"土 24° 是刻意决定"写进文档（与 Q3 合并），**避免以后被当成 bug 提回**。

## Q2：上海木「取不满但明示」可否作终态？

**裁决：可以作终态。** 三条理由：

1. **物理上无法补齐** —— 证据链已成立（见 §三）
2. **回执 §3.4 已预留此路径** ——"接受取不满，但降级展示并标注"
3. **明示 notice 比静默少显示诚实得多** —— 而且你写的"**非数据遗漏**"这句很关键，
   它预先回答了用户"是不是漏了"的疑问

**但要求两条**：

- notice **始终可见**，不得折叠或隐藏在"展开更多"里
- notice 的样式**不能渲染成错误/警告红**（现在用琥珀色，合适）——
  它是"说明"，不是"报错"

## Q3：是否把「方位门控与卦位标签分离」补入文档？

**裁决：需要 —— 而且应该写进《验收标准与红线》，不只写产品文档。**

因为这是一条**可复用的设计原则**：

> **当"标签的划分标准"与"判据的划分标准"不同时，必须显式说明二者关系，
> 不能让用户以为"标签就是判据"。**

具体到这里：

| | 划分 | 标准 | 用途 |
|---|---|---|---|
| **卦位**（8 等分，45°） | 传统八卦 | **方位标签**（"东南·巽木"） |
| **门控**（5 类，84°/24°） | 服务操作需求 | **五行判定**（每类可取满） |

**同一城市因此可能"卦位属土、门控属木"** —— 这不是 bug，是两套标准并存。
**必须并列展示 + 一句说明**，否则用户会认为是矛盾。

# 五、发现一处小问题：`tsx` 不在依赖里

```json
"verify": "npx tsx scripts/test-geo-accept.mjs && npx tsx scripts/test-wealth-accept.mjs && npx tsx scripts/test-regression.mjs"
```

我查了 `package.json`：**`tsx` 既不在 `dependencies` 也不在 `devDependencies`。**

**后果**：本机跑得通（`npx` 命中了本地缓存），但在**新环境 / CI** 上
`npx tsx` 会去**临时下载** tsx —— 慢，而且离线会失败。

**建议**：把 `tsx` 加为 `devDependencies`，并把 `verify` 改为直接用本地二进制：

```json
"devDependencies": { "tsx": "^4.x" },
"scripts": { "verify": "tsx scripts/test-geo-accept.mjs && tsx scripts/test-wealth-accept.mjs && tsx scripts/test-regression.mjs" }
```
