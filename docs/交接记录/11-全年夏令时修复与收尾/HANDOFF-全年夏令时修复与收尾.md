# 一、P0：全年夏令时（year-round DST）导致不剥 DST

## 1.1 先澄清：**与半球无关**

用户问"北半球夏天=南半球冬天，南半球测试是否不准"。**实测：半球没有问题。**

`min(1月, 7月)` 不依赖哪个半球是夏天 —— 夏令时恒为 +1（往大走），
**数值较小的那个永远是标准时**：

| 时区 | 1月 | 7月 | min | 自动选中 |
|---|---|---|---|---|
| 纽约（北半球夏令 7月） | −5 | −4 | **−5** | 1月 |
| 悉尼（南半球夏令 1月） | +11 | +10 | **+10** | **7月** |
| 阿德莱德（半小时） | +10.5 | +9.5 | **+9.5** | 7月 |
| 豪勋爵岛（30分夏令） | +11 | +10.5 | **+10.5** | 7月 |

**南半球自动落在非夏令那一侧，无需特判。** 现有悉尼用例已给 `−60` ✓

## 1.2 但同一机制有真缺陷：**前提是"两个采样点至少有一个不是夏令时"**

**美国「战时时间」War Time：1942-02-09 ~ 1945-09-30，全年 UTC−4，没有冬季回落。**

```
America/New_York 1943  1月 −4   7月 −4  →  min −4   真实标准 −5   ★ 前提破裂
America/New_York 1944  1月 −4   7月 −4  →  min −4   真实标准 −5   ★
America/Chicago  1943  1月 −5   7月 −5  →  min −5   真实标准 −6   ★
Europe/London    1943  1月 +1   7月 +2  →  min +1   真实标准  0   ★（英战时双夏令时）
```

**后果**：

```
纽约 1943-07-15 13:30（仅时区路径）
  现行：假定经度 −60°，实际偏移 UTC−4 → 校正 0 分
  应为：−60 分（战时时间 = 标准时 +1h，须剥掉）
  → ★ 差 60 分钟，足以改变时柱
```

**根因是信息缺失，不是算法不够聪明**：

> **"标准偏移"是 tzdata 的元数据，无法从纯偏移采样里推出来** ——
> **"全年夏令时"与"标准偏移本身就是 −4"在采样上不可区分。**
> 所以换任何采样方案（±6 个月、12 个月）都救不了，**必须换推算基准**。

## 1.3 ★ 修法（我已实测 9/9，直接用）

**把"标准偏移"的推算基准从【出生年】改为【固定参考年】。**

```ts
/** 标准偏移的推算基准年。
 *  为什么要固定：夏令时是季节性的，但【战时/特殊时期可能全年都是夏令时】——
 *  此时"取出生年 1 月与 7 月的最小值"会取到夏令时偏移本身，导致 DST 不被剥离。
 *  用近年正常年份作基准可绕开该问题，且结果确定（便于断言）。
 *  若某时区此后变更其标准偏移，可提升此常量。 */
const STD_REF_YEAR = 2020

export function standardMeridianLng(zone: string, _when?: BirthMoment): number {
  const probe = (month: number) =>
    getUtcOffsetHours(zone, { year: STD_REF_YEAR, month, day: 15, hour: 12, minute: 0 })
  return Math.min(probe(1), probe(7)) * 15
}
```

> **注意**：`when` 参数从此不再参与推算。**保留签名**以免破坏调用方，
> 但加注释说明它已被刻意忽略 —— **这属于 §8.4.4「刻意的设计决定要显式说明」**。

**参考年不敏感**（我实测 2015 / 2018 / 2020 / 2024 / 2030 都是 9/9）——
所以不必纠结具体选哪一年，**只需是个"规则正常的近年"且写死**（写死才能保证断言确定）。

## 1.4 ★ 修法效果（我实测，请照此对表）

| 用例 | 现行(出生年) | **修法(固定年)** | 期望 |
|---|---|---|---|
| 纽约 1943-07-15（战时） | 0 ✗ | **−60 ✓** | −60 |
| 纽约 1944-07-15（战时） | 0 ✗ | **−60 ✓** | −60 |
| 芝加哥 1943-07-15（战时） | 0 ✗ | **−60 ✓** | −60 |
| 伦敦 1943-07-15（双夏令时） | −60 ✗ | **−120 ✓** | −120 |
| 纽约 1990-07-15（正常夏令） | −60 ✓ | −60 ✓ | −60 |
| 纽约 1990-01-15（正常冬季） | 0 ✓ | 0 ✓ | 0 |
| 悉尼 1990-01-15（南半球） | −60 ✓ | −60 ✓ | −60 |
| 北京 1988-07-15（中国夏令） | −60 ✓ | −60 ✓ | −60 |
| 阿德莱德 1990-01-15（半小时） | −60 ✓ | −60 ✓ | −60 |

```
现行正确 5/9  →  修法正确 9/9
```

## 1.5 ★ 必须补的回归用例（依 §8.6 牙口）

**前三条天然有牙**（出生年法给出 0 / 0 / −60，与期望不同 → 断言必红）：

```
America/New_York  1943-07-15 13:30  仅时区  → 校正 −60，标准经线 −75
America/Chicago   1943-07-15 13:30  仅时区  → 校正 −60，标准经线 −90
Europe/London     1943-07-15 13:30  仅时区  → 校正 −120，标准经线 0
```

**并加牙口自检**（仿 `test-solar-time.mjs` 既有做法）：
断言"用出生年推算时结果不同" —— 防止后人把参考年改回出生年而**无声退化**。

**并加注释说明日期是刻意选的**（§8.6.1）：
**这三条覆盖"全年夏令时"这个唯一能区分两种推算基准的场景。**

# 二、P1：时区校验的纵深兜底

## 2.1 现状

`isValidZone` 已存在 ✓，四个 route 入口也校验了 ✓。
**但 `getUtcOffsetHours` 内部没有兜底** —— 非法 zone 传进去会直接抛 `RangeError`。

## 2.2 为什么还要兜底

zone 字符串**不只从"手动时区"一个入口进来**：

| 入口 | 现状 |
|---|---|
| 手动时区输入框 | ✅ route 已校验 |
| **城市记录的 `z` 字段** | 我实测 355 个 zone **全部合法** ✓（但依赖构建脚本正确） |
| **旧客户端传的 `birthplace` 城市名** | 查表得到，风险同上一行 |
| 未来若加 URL 参数 / 分享链接 | ⚠️ 未覆盖 |

## 2.3 改法

在 `getUtcOffsetHours` 内部兜底：

```ts
try {
  // …原有 Intl 计算…
} catch {
  console.warn(`[solarTime] 非法时区「${zone}」，降级为 ${DEFAULT_ZONE}`)
  return getUtcOffsetHours(DEFAULT_ZONE, when)   // 或直接按默认时区算
}
```

**成本极低，收益是"任何路径上的脏 zone 都不会变成 500"。**
（注意防递归：内部走一个不再校验的私有实现。）

# 三、P2：`toTrueSolarTime` 改用 UTC 构造

## 3.1 现状（仍用本地 getter）

```ts
const d = new Date(year, month - 1, day, hour, minute, 0)   // 本地
const a = new Date(d.getTime() + offsetMin * 60000)
return { year: a.getFullYear(), … a.getHours() … }          // 本地
```

**理论风险**：若**服务器本地时区**本身有夏令时，且平移跨越该时区的 DST 切换点，
读回的钟表时间会差 1 小时。

## 3.2 我实测**未复现**（所以是加固，不是缺陷）

```
TZ=UTC               → 与手工 UTC 核算一致
TZ=America/New_York  → 与手工 UTC 核算一致（未复现偏差）
```

生产环境通常是 UTC（无 DST），本就安全。

## 3.3 改法（可选，成本极小）

改用 `Date.UTC(...)` 构造 + `getUTC*()` 读取，使实现**不依赖服务器时区**。

# 四、★ P1 核查项：`AI_API_KEY` 在运行环境是否生效

**这一条不是代码改动，但可能比前面三条都重要。**

## 4.1 问题

你在 `HANDOFF-BACK-出生地简化与全球城市库回传.md` §三-2 写：

> 「`verify:ai` 本轮未跑：四 API 实测环境**未配置 `AI_API_KEY`**，自动回退规则版。」

## 4.2 为什么要查

**如果运行环境真的读不到 `AI_API_KEY`，那么**：

> 用户看到的是**规则版文案**，不是 AI 解读 ——
> **前面几轮在 AI 合规上做的全部工作（禁绝对标签、依据分级、结构病、重试回退）
> 都没有到达用户面前。**

这正是第 08 轮那个教训的另一面：**"测试通过"不等于"产品在跑那条路"**。

## 4.3 要查清的三件事

```
① .env.local 里的 AI_API_KEY 是否存在且非空（我方此前实测 key 有效、两个 endpoint 均 200）
② dev server / 生产环境的启动方式是否会加载它
   —— 注意端口 3000 上那个【早前会话遗留的 dev server】(PID 19412)，
      它可能是在 key 配置之前启动的，或工作目录不同
③ AI 调用失败时是否【有日志】
   —— 现在"自动回退规则版"是静默的，用户与我们都不知道
```

**第 ③ 条建议做成代码改动**：AI 回退时**打印明确警告**（而非静默）。
**静默降级是危险的** —— 它让"AI 没跑"这件事不可见。

## 4.4 交付要求

贴出：**一次真实批命调用的响应**，标明**是否走了 AI 路径**（以及 token 用量，若走）。
