# P0 缺陷报告：`paipan` 在 23:00–24:00 的四柱自相矛盾

> **发现者**：DeepSeek 侧（2026-10-07）
> **发现场景**：Part B 流日引擎验收时**探边界**撞到（**不在该轮交付范围内**）
> **性质**：**既有缺陷**（在 `paipan` / `lunar-javascript` 的 `EightChar` 处，非本轮引入）
> **影响面**：**23:00–24:00 出生者 ≈ 1/24 ≈ 4.2%**
> **严重度**：**P0** —— 用户拿到的是**四柱互相打架的命盘**

---

# 一、现象

对同一出生时刻，`paipan` 输出的**日柱与时柱用了不同的换日约定**：

```
2026-01-06 23:30  →  日 庚辰   时 戊子
2026-01-07 00:30  →  日 辛巳   时 戊子
```

**两个时刻的时柱相同（戊子），但日柱不同（庚辰 / 辛巳）。**

## 为什么这是矛盾（**与流派无关**）

**五鼠遁**是硬规矩 —— 时干由**日干**唯一决定：

```
甲己 → 甲子      乙庚 → 丙子      丙辛 → 戊子
丁壬 → 庚子      戊癸 → 壬子
```

所以：

| 日柱 | 子时的时柱**必须**是 |
|---|---|
| 庚辰日 | **丙子** |
| 辛巳日 | **戊子** |

**而 2026-01-06 23:30 我们输出的是 日庚辰 ＋ 时戊子**
→ **日柱说是「庚」日，时柱却按「辛」日推的**。

> **无论采用哪套换日约定，日柱与月柱/时柱都必须彼此自洽。**
> **现在是两套混用 —— 所以这是 bug，不是流派差异。**

---

# 二、严格验证（约定无关的判据）

我写了一个**不依赖任何流派假设**的检查：**对每个时刻，用该时刻输出的「日干」按五鼠遁推出应有的「时干」，与输出的时干比对。**

```
扫描 240 个时刻（5 个日期 × 12 时辰 × 2 个分钟）
违反五鼠遁 10 处 —— ★ 全部落在 23 点

2026-01-06 23:00   日庚辰  时戊子  ← 应为 丙子
2026-01-06 23:30   日庚辰  时戊子  ← 应为 丙子
2026-01-07 23:00   日辛巳  时庚子  ← 应为 戊子
2026-01-07 23:30   日辛巳  时庚子  ← 应为 戊子
2026-06-15 23:00   日庚申  时戊子  ← 应为 丙子
2026-06-15 23:30   日庚申  时戊子  ← 应为 丙子
2024-02-29 23:00   日癸亥  时甲子  ← 应为 壬子
2024-02-29 23:30   日癸亥  时甲子  ← 应为 壬子
1991-04-12 23:00   日壬子  时壬子  ← 应为 庚子
1991-04-12 23:30   日壬子  时壬子  ← 应为 庚子
```

**10/10 都在 23 点，其余 230 个时刻全部自洽。** 规律极其干净。

---

# 三、根因

```
日柱  ← EightChar.getDay()
        用【民用日 00:00】换日 → 23:30 仍算当日（庚辰）

时柱  ← EightChar.getTime()
        其内部用【晚子时 23:00】换日 → 时干按次日日干（辛）推 → 戊子
```

**`lunar-javascript` 的 `EightChar` 内部对不同柱使用了不同的 `getDayGanIndex*` 变体**
（该库有 `getDayGanIndex()` / `getDayGanIndexExact()` / `getDayGanIndexExact2()` 等，
分别对应不同换日约定）。**我们直接取了两个默认值，而它们不一致。**

# 四、影响

| 项 | 说明 |
|---|---|
| **谁受影响** | **23:00–24:00 出生者** ≈ **4.2%** 的用户 |
| **症状** | 命盘**日柱与时柱不匹配** —— 任何懂命理的用户一眼能看出错 |
| **静默性** | **完全静默** —— 页面正常显示，无任何报错 |
| **连带影响** | 所有基于 `日主`/`日干` 的解读与 `时柱` 的解读**互相矛盾**；大运/流年推算亦受牵连 |

> **这正是「我不想做一个给别人提供错误信息的工具」最怕的那类问题**：
> **看起来完全正常，但盘本身是错的。**

# 五、修法：**先定约定，再统一**

## 5.1 两套约定，必须**二选一**，不能混用

| | **A. 晚子时（23:00 换日）** | **B. 早子时（00:00 换日）** |
|---|---|---|
| 传统性 | ✅ **主流传统**（子时 = 23:00–01:00，日换于子时之初） | 现代简化 |
| 23:30 的日柱 | 次日（辛巳） | 当日（庚辰） |
| 23:30 的时柱 | 戊子（辛日子时）✓ **我们已是这个** | 丙子（庚日子时） |
| 需改 | **日柱** | **时柱** |

## 5.2 ★ 我建议 **A（晚子时 23:00）**

理由：

```
① 它是传统主流 —— 子时定义为 23:00–01:00，日柱应换于子时之初
② 我们的时柱【已经是】这个约定 → 改动面更小
③ 主流排盘软件多采此约定，用户对照时不会觉得我们"和别人不一样"
```

**但这是命理约定决策，应由你拍板**（§8.4.4：刻意选择要显式说明）。

## 5.3 ★ 无论选哪个，都必须加一条**常驻断言**

新建 `scripts/test-ganzhi-consistency.mjs` 并纳入 `verify`：

```
判据：对 24 时辰 × 多个日期，用输出的「日干」按五鼠遁推出应有的「时干」，
      与输出的「时干」逐一比对，必须 100% 一致。

这个判据【不依赖流派】—— 所以它同时守住 A 与 B 两种约定，
只抓「日柱与时柱自相矛盾」这一件事。

★ 并加牙口自检（§8.6）：构造一个「日柱或时柱被单独偏移」的坏值，
   断言必须翻红 —— 否则它只证明了"两个死值相等"。
```

**同类可一并加**：**月柱 ← 五虎遁（年干推月干）** 的自洽断言。
四柱各有自己的推导硬规矩，**目前只有日↔时这一条被验出问题**，
但年↔月那条从未被断过 —— **建议一并补上**。

# 六、为什么之前没被发现

我们的边界工作（事故 27、28）**全部集中在「时区偏移导致的时辰边界」**：

```
真太阳时校正 −56 分 → 出生时刻跨时辰 → 已测 ✓
夏令时剥离        → 已测 ✓
```

**但从未测过「时辰自身的换柱点」** —— 即 **23:00 这个子时边界**。

> **教训（建议入总纲）**：
> **列边界时，要把「每一柱各自的换柱点」穷举**，而不是只测"外部扰动（时区/夏令时）造成的边界"。
>
> | 柱 | 换柱点 |
> |---|---|
> | 年柱 | 立春（节气） |
> | 月柱 | 十二节（节气） |
> | **日柱** | **子时（23:00 或 00:00）** ← **本次漏掉的就是这个** |
> | 时柱 | 每个整时辰（2 小时） |
>
> **只测"扰动"不测"换柱点本身"，会留下整类盲区。**

---

# 七、建议的处置顺序

| # | 事项 | 依赖 |
|---|---|---|
| 1 | **你拍板约定 A 还是 B** | 命理决策，你定 |
| 2 | 统一 `日柱` 与 `时柱` 的换日约定 | 取决于 1 |
| 3 | **加五鼠遁自洽断言 ＋ 牙口自检**，纳入 `verify` | 无 |
| 4 | **加五虎遁（年→月）自洽断言** | 无 |
| 5 | 回归：确认**非 23 点**的既有时刻输出**零变化**（尤其你本人的盘 1991-04-12 03:10） | 无 |

**★ 第 3、4 条不依赖第 1 条** —— **可以立刻做**，
而且它们会把"到底哪套约定"这件事**变成可验证的**，而不是靠记忆。

**★ 这属于独立缺陷，不阻塞 Part B 继续推进**（流日引擎本身是对的）。
但**它是 P0 —— 建议插入在 180 条文案之前**，因为它影响的是**已经上线的排盘**。
