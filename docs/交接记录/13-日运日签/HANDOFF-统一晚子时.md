# 二、★ 紫微：两处入口，且要顺带修一个 P0

## 2.1 全部调用入口（我方实测扫描）

```
src/lib/ziwei.ts:172   paipanZiwei   → astro.astrolabeBySolarDate(dateStr, timeIndex, gender)
src/lib/ziwei.ts:515   analyzeZiwei  → astro.astrolabeBySolarDate(`${chart.input.year}-…`, …)
```

**只有这两处**（其余 `chart.input.*` 出现在 `aiAnalysis/aiHemun/aiZiwei`，是给 AI 提示词
拼「公历…」用的展示文本，不参与计算 —— **本轮不动**）。

## 2.2 ★★ 既有 P0：两处的**输入不同**，所以紫微盘被算成了两个

```ts
// 入口一 paipanZiwei（ziwei.ts:163-172）—— 用【真太阳时校正后】的值
const a = new Date(d.getTime() + timezoneOffsetApplied * 60000)
year = a.getFullYear(); … hour = a.getHours()
const dateStr = `${year}-${month}-${day}`          // ← 校正后
…

// 入口二 analyzeZiwei（ziwei.ts:515-518）—— 用【原始未校正】的值
astro.astrolabeBySolarDate(
  `${chart.input.year}-${chart.input.month}-${chart.input.day}`,   // ← 原始
  chart.input.hour === 23 ? 0 : Math.floor((chart.input.hour + 1) / 2),
  …
)
```

**而 `ZwChart.input` 存的就是原始 input**（`ziwei.ts:213` `return { input, … }`，
`input` 从未被校正值覆盖）。

### 实测证据（我方）

```
乌鲁木齐 1991-04-12 03:10（经度 87.6，偏移 −130 分）
  原始   03:10  时辰索引 2（寅时）
  校正后 01:00  时辰索引 1（丑时）

  入口二用的盘（原始值构建）→ 命宫主星：廉贞,七杀
  入口一返回的盘（校正值构建）→ 命宫主星：（空宫）
  ★ 两盘不同
```

### 后果

> **用户在紫微页看到的「盘」是按校正后时辰构建的，
> 但盘上显示的「大限／流年」是按原始时辰构建的另一张盘算出来的。**
> **两者不是同一个盘。**

### 影响面（我方取样）

| 城市 | 真太阳时偏移 | 48 个取样时刻中跨时辰 |
|---|---|---|
| 喀什 | −176 分 | **100%** |
| 乌鲁木齐 | −130 分 | **100%** |
| 拉萨 | −116 分 | **100%** |
| 成都 | −64 分 | 75% |
| 昆明 | −69 分 | 75% |
| 重庆 | −54 分 | 50% |
| 纽约 | −56 分 | 50% |
| 哈尔滨 | +26 分 | 0% |

**→ 偏移越大越严重。乌鲁木齐/拉萨/喀什出生的用户【每一次】都拿到矛盾的盘与运限。**

## 2.3 修法：把「构建参数」变成**单一事实源**（依 §8.5.1）

**根因是同一个对象被构建了两次、且两次的输入不同。**

**建议**（最小改动、且从结构上消除分叉）：

```ts
// ZwChart 增加两个字段：本轮构建 iztro 盘所用的【最终参数】
export interface ZwChart {
  …
  /** ★ 构建 iztro 盘所用的公历日期（已含真太阳时校正 ＋ 晚子时推进） */
  ziweiDateStr: string
  /** ★ 构建 iztro 盘所用的时辰索引（0=子时） */
  ziweiTimeIndex: number
}
```

- **入口一**：算出 `dateStr` / `timeIndex` 后，**存进返回的 ZwChart**
- **入口二**：**改为读 `chart.ziweiDateStr` / `chart.ziweiTimeIndex`**，**不再从 `chart.input` 重新推导**

**这样两处必然用同一组参数**，日后任何改动都只需动一处 ✓

> **并在入口二处加注释**（§8.4.4）：
> 「★ 禁止从 chart.input 重新推导 —— 那是原始未校正值，
> 曾经导致返回的盘与运限所用的盘不是同一个（见 §2.2）。」

## 2.4 晚子时推进（入口一）

在**真太阳时校正之后**、构造 `dateStr` 之前：

```ts
let dateStr = `${year}-${month}-${day}`
// ★ 晚子时：当地 23:00 起即归次日（与 paipan 的 setSect(1) 同一约定）
if (hour === 23) {
  // 用 UTC 做日历日 +1，避免服务器时区/DST 干扰
  const t = new Date(Date.UTC(year, month - 1, day + 1))
  dateStr = `${t.getUTCFullYear()}-${t.getUTCMonth() + 1}-${t.getUTCDate()}`
}
const timeIndex = hour === 23 ? 0 : Math.floor((hour + 1) / 2)   // 不变
```

**⚠️ 注意**：
- 推进必须用 **`Date.UTC` 做日历日 +1**，不要用「毫秒 + 86400000」（跨 DST 会错）
- `timeIndex` **保持 0**（23 点仍是子时）—— 变的只是**归哪一天**
- 推进后要**同时写进 `ziweiDateStr`**（§2.3）

# 三、日运归日：晚子时（`daily.ts` 新增）

## 3.1 现状

`daily.ts` 目前只有 `liuRiOf(y,m,d)`（**固定 12:00 构造**，取该公历日的日柱）、
`DAILY_TAGS`、`jiaziIndex`。**「今天」的判定尚未实现** ✓ 本轮补上。

## 3.2 新增：`dailyDateInZone(zone, now?)`

```ts
/**
 * 取某时区「当前」的归日。
 * ★ 晚子时：当地 23:00 起即算次日（与 paipan/ziwei 同一约定）。
 * 返回的公历日期可直接传给 liuRiOf()。
 */
export function dailyDateInZone(
  zone: string,
  now: Date = new Date()
): { year: number; month: number; day: number }
```

**实现要点**：

```
① 用 Intl.DateTimeFormat 取该时区的当地 年/月/日/时
   （solarTime.ts 已有同样用法可参考；非法 zone 走 isValidZone 降级 DEFAULT_ZONE）
② 若 当地小时 >= 23 → 日历日 +1（用 Date.UTC 构造，避免 DST）
③ 返回调整后的 {year, month, day}
```

**★ 关键**：`liuRiOf` 保持**固定 12:00 构造不变**（它取的是"某公历日的日柱"，
12:00 远离 23:00 边界，与 sect 无关）。**"归哪一天"这件事由本函数负责，两者职责分离** ✓

## 3.3 UI 必须注明（否则用户会困惑）

# 四、★ 归日一致性断言（含牙口）

> **依 §8.5：同一输入，遍历所有入口，结果必须一致。**
> **自洽只保证模块内部不矛盾，不保证模块之间不打架。**

## 4.1 判据形状（**刻意选成"约定无关"的形式**）

**不要写死"23:30 应属次日"**（那是把约定抄进断言，改约定就要改断言）；
**要断言「同一个子时的两个时刻，必须得到同一个归日」** —— 这条对两种约定都成立，
只抓"模块之间打架"这一件事：

```
对若干含 23:xx 的时刻对（同一天的 23:30 与次日的 00:30）：

  ① 八字：paipan(d, 23:30) 的日柱  ≡  paipan(d+1, 00:30) 的日柱
  ② 紫微：paipanZiwei(d, 23:30).lunarDate  ≡  paipanZiwei(d+1, 00:30).lunarDate
  ③ 日运：dailyDateInZone(zone, d 23:30 当地)  ≡  dailyDateInZone(zone, d+1 00:30 当地)
  ④ ★ 跨模块：三者的"归日"指向同一天

—— 全部必须相等。任一模块还是早子时，①②③ 立刻翻红。
```

**日期窗口建议**：含普通日、**农历月末（冬月三十→腊月初一）**、年末、闰日，
以及**带真太阳时偏移的时刻**（覆盖 §2.2 那个二次构建缺陷）。

## 4.2 ★ 牙口自检（§8.6）

```
· 把任一入口的归日偏移一天 → 断言必须翻红
· 特别地：把 analyzeZiwei 改回从 chart.input 重新推导 →
  【必须翻红】—— 这条直接守住 §2.2 那个 P0 不复发
```

**★ 第二支尤其重要** —— 它是"两处入口用同一组参数"的守护断言（§8.5.1）。

# 六、必须避免

- ❌ **不得只改入口一（`paipanZiwei`）而漏掉入口二（`analyzeZiwei`）** —— §8.5 的经典遗漏
- ❌ **不得让 `analyzeZiwei` 继续从 `chart.input` 重新推导** —— 那是原始未校正值

- ❌ **不得改 `liuRiOf` 的 12:00 固定构造** —— 它取的是"某公历日的日柱"，与归日职责分离

- ❌ **不得声明"紫微盘相同"而不比星曜** —— 只比宫位干支是假绿（**§8.6.5，事故 33**）
- ✅ **必须给出快照 diff 证明非 23 点零变化**
