# 三、这需要一次【**产品级**】的换日约定决策

**现状：产品里同时存在两种归日约定，且它们服务同一个输入（出生时刻）。**

| 模块 | 现在的约定 | 23:30 归属 |
|---|---|---|
| **八字排盘** | **晚子时（23:00 换日）** | 次日 ✓ 已修 |
| **紫微**（iztro） | **早子时（00:00 换日）** | 当日 |
| **日运**（计划中） | **民用日 00:00** | 当日 |

## 3.1 ★ 建议：**全产品统一为晚子时**

```
① 传统主流 —— 子时定义为 23:00–01:00，日换于子时之初；
   八字与紫微在这一点上传统是【一致】的（iztro 的默认只是库的选择，非流派定论）
② 八字已改，改紫微＝改动面更小
③ 用户最容易发现的跨模块矛盾，就是同一时刻两处说不一致
```

**具体做法**（与你的建议一致）：**hour === 23 时，先把 dateStr 推进一天再传 iztro**，
并保留 `timeIndex = 0`（子时）。

## 3.2 ⚠️ 但**日运**要单独想清楚 —— 它与前两者不是一回事

```
排盘的归日  回答：「你【出生】在哪一天（命理意义）」
日运的"今天" 回答：「用户日历上的【今天】」
```

**在 23:00–24:00，这两个答案会分开**：

| | 23:30 打开日运 |
|---|---|
| 民用日 00:00（设计稿现案） | 显示「今日 = 庚辰日」 |
| 晚子时 23:00（若统一） | 显示「今日 = 辛巳日」（即次日） |

**设计稿 §2.3 选民用日的理由是「用户 23:30 打开会看到明天的运势 → 困惑」。**
**但那个论证写在八字还是早子时的时候 —— 现在前提变了。**

**我的建议**：**日运也统一晚子时**，理由：

```
① 懂命理的用户本来就知道「过了 23 点就是次日」—— 不困惑，反而觉得我们对
② 不懂的用户在 23 点后看到"新的一天"，也说得通（日历上确实快到了）
③ 三处一致，用户对照任何两个模块都不会打架
④ UI 注明一句即可：「子时（23:00）起为次日」
```

**但这是产品决策，请你拍板。** 若你倾向保留"日运按民用日"，
**则必须在 UI 明说「排盘按子时换日、日运按自然日」**，否则这就是个可见矛盾。

## 3.3 ★ 并加一条【归日一致性断言】

依总纲 §8.5 —— **同一输入，遍历所有入口，归日必须一致**：

```
断言：对若干含 23:xx 的时刻，
      八字 paipan 的日柱所属日  ≡  紫微所用农历日所属日  ≡  日运所取日
      （三处必须指向同一天）

★ 并加牙口自检：把任一处的归日偏移一天，断言必须翻红。
```

**这条断言比"各模块自己自洽"更重要** ——
**自洽只保证每个模块内部不矛盾，不保证模块之间不打架。**
