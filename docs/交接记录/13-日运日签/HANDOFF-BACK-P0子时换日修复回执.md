# 二、逐条回应

## 2.1 库源码核对（先证根因，再动手）

读 `node_modules/lunar-javascript/lunar.js`，与你的报告完全一致，且更精确：

```js
// _computeDay（lunar.js:743）
dayGanIndex / dayGanIndexExact2  ← 民用日正午，00:00 换日（相同值）
dayGanIndexExact                ← 时刻在 23:00–23:59 则 +1（23:00 换日）

// _computeTime（lunar.js:769）
timeGanIndex = (dayGanIndexExact % 5 * 2 + timeZhiIndex) % 10   ← 时干按【Exact/晚子时】

// EightChar（默认 sect=2）
getDay() sect2 → getDayInGanZhiExact2   ← 民用日
getTime()      → lunar.getTimeInGanZhi  ← 晚子时   → 23:00–24:00 矛盾
```

## 2.2 修复（paipan.ts:94-99）

取得 eightChar 后立即：

```ts
eightChar.setSect(1)
```

sect=1 时 getDay() → Exact（23:00 换日），与 getTime() 同源。影响面已逐一核实：

| 链路 | 是否受 setSect 影响 |
|---|---|
| 年柱 getYear / 月柱 getMonth | 否（两 sect 均走 Exact：立春/节气） |
| 日柱 getDay | 是（本修复） |
| 时柱 getTime | 否（本就按晚子时，与库的 sect 无关） |
| 起运 getYun | 否（sect 由第二参数独立传入；paipan 只传一个参数，内部归一恒为 1） |
| 胎元/命宫/身宫 | 否（只用月、年及时支，不用日） |

约定与理由写进了代码注释（§8.4.4）。

## 2.3 常驻断言（scripts/test-ganzhi-consistency.mjs）

插入 verify（entry-consistency 之后、daily 之前），判据**流派无关**：

- 扫描 **7 日期 × 48 时刻 = 336 时刻**（每小时 :00/:30；日期含普通日、立春前夕、夏至、闰日、本命日、春分）；

# 四、承认缺项

1. **紫微模块的换日约定未跟随**：iztro 现走「23 点归**当日**子时」（早子时，内部自洽，无五鼠遁问题）。八字改晚子时后，23:00–24:00 出生者在八字与紫微中**跨模块日用不同**。是否把紫微也推进次日（自行把 dateStr ＋1 再传 iztro）属独立命理决策，本轮未动，见 §五。
2. 断言扫描固定为 **7 个日期**，非穷举全年；受保护的是「与流派无关的两条硬规矩」，新日期违规同样会被公式抓到，只是没有显式样例。
3. 晚子时改日柱会连带改变这批用户（4.2%）的**日主**及其全部下游解读（格局/喜忌/大运方向）——这是修正错误而非可选项，但意味着他们重测会看到与旧盘不同的结果，产品侧若要公告需自行拟措辞。
