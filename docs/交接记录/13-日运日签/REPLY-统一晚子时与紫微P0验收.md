# 二、⚠️ 需补强之一：`dailyDateInZone` 未防护 Intl 的 `'24'`

## 现状

```ts
const hour = get('hour')   // 多数环境午夜为 '00'；个别环境为 '24'
if (hour >= 23) { …日历日 +1… }
```

**你自己在注释里写了这个风险，但没有防护。**

```
若环境返回 '24'（hour12:false 在部分 ICU 实现下把午夜给成 24）
  → 24 >= 23 成立 → 【午夜被推进一天】✗
```

## 我方实测：**本环境安全，但这不构成保证**

```
本环境 Intl 在午夜返回什么：
  Asia/Shanghai     出现 '24': false   出现 '00': true   ✓
  America/New_York  出现 '24': false   出现 '00': true   ✓
  UTC               出现 '24': false   出现 '00': true   ✓
```

**所有 9 个边界用例全对** ✓（22:59 / 23:00 / 23:59 / 00:00 / 00:01 / 12:00 × 两个时区）

**但**：`hour12: false` 在不同 ICU/V8 版本下**历史上行为不一致**，
这是已知问题；**它是环境相关的，可能在升级 Node 或换运行时后改变** ✓

## 修法（1 个字符）

```ts
const hour = get('hour') % 24      // '24' → 0，环境无关
```

**或**把 `hour12: false` 换成显式的 `hourCycle: 'h23'` ✓

**成本 ≈ 0，收益是"不依赖运行时版本"** ✓

# 三、⚠️ 需补强之二：**你的测试抓不到它** —— 因为测试自己做了归一化

## ★★ 这条比 §二 本身更重要

你的测试辅助函数（`test-dayboundary-accept.mjs:28`）：

```js
let hh = g('hour'); if (hh === 24) hh = 0      // ← 辅助函数归一化了 '24'
```

**而生产代码 `dailyDateInZone` 没有归一化** ✗

**→ 即使运行环境返回 '24'，测试的 `atLocal` 会正确找到时刻、断言全部通过，
而生产函数仍会把午夜推进一天。测试替生产挡掉了缺陷。**

## 而且子时对里**没有 00:00 整点**

```js
const NOW_PAIRS = [
  [[…, 23, 30], […, 0, 30], …],   // ← 23:30 与 00:30
  …
]
```

**'24' 只在【恰好午夜 00:00】出现** —— 而你的时刻对用的是 **23:30 与 00:30**，
**两头都避开了整点** ✗

**→ 这是双重盲区**：辅助函数挡一层、用例不覆盖再挡一层 ✓

## 修法

```
① dailyDateInZone：加 % 24（环境无关）
② 子时对里补一个【含 00:00 整点】的用例：
     例如 [[2026,1,6,23,0], [2026,1,7,0,0]]
     —— 它既覆盖整点，也覆盖 23:00 边界
③ 测试辅助函数【不再替生产做容错】：
     atLocal 保留归一化（它需要精确命中），
     但断言里应【显式比对 dailyDateInZone 在整点的返回】，
     使生产的容错缺失能被抓到
```
