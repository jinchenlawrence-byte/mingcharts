# P0 缺陷报告：紫微盘被算两次，两次输入不同

> **发现者**：DeepSeek 侧（2026-10-07）
> **发现场景**：为「统一晚子时」任务书**扫描 iztro 全部调用入口**（依 §8.5）时撞到
> **性质**：**既有缺陷**（非本轮回合引入）
> **严重度**：**P0** —— 用户看到的盘，与盘上「大限/流年」所用的盘，**不是同一个**
> **影响面**：**带真太阳时偏移的城市，最高 100% 中招**（见 §三）
> **与「子时换日」的关系**：**同一个类** —— 同一份输入被两条路径分别加工，且两条路径拿到的输入不同

---

# 一、现象

`src/lib/ziwei.ts` 里**同一个 iztro 盘被构建了两次，而且两次用的输入不同**：

```ts
// 入口一 paipanZiwei（:163-172）—— 用【真太阳时校正后】的值
const a = new Date(d.getTime() + timezoneOffsetApplied * 60000)
year = a.getFullYear(); month = a.getMonth()+1; day = a.getDate(); hour = a.getHours()
const dateStr = `${year}-${month}-${day}`
const astrolabe = astro.astrolabeBySolarDate(dateStr, timeIndex, gender)

// 入口二 analyzeZiwei（:515-518）—— 用【原始未校正】的值
const astrolabe = astro.astrolabeBySolarDate(
  `${chart.input.year}-${chart.input.month}-${chart.input.day}`,
  chart.input.hour === 23 ? 0 : Math.floor((chart.input.hour + 1) / 2),
  chart.input.gender === 1 ? '男' : '女'
)
```

**而 `ZwChart.input` 存的就是原始 input**：

```ts
// ziwei.ts:213
return { input, timezoneOffsetApplied, lunarDate: astrolabe.lunarDate, … }
//       ↑ 从未被校正值覆盖
```

# 二、实测证据

```
乌鲁木齐 1991-04-12 03:10（经度 87.6，真太阳时偏移 −130 分）
  原始   03:10  时辰索引 2（寅时）
  校正后 01:00  时辰索引 1（丑时）

  入口二所用的盘（原始值构建）→ 命宫主星：廉贞,七杀
  入口一返回的盘（校正值构建）→ 命宫主星：（空宫）
  ★ 两盘不同
```

**返回体里同时含这两样：**

```jsonc
{
  "chart":    { /* 按【校正后】时辰构建 —— 命宫空宫 */ },
  "analysis": { /* 其"大限/流年"按【原始】时辰构建 —— 命宫廉贞七杀 */ }
}
```

**→ 用户在紫微页看到的盘，与盘上算出的运限，来自两张不同的盘。**

# 三、影响面

**触发条件**：该次出生的**真太阳时校正跨了时辰边界**。
偏移越大越容易跨（时辰宽 2 小时 = 120 分）。

| 城市 | 真太阳时偏移 | 48 个取样时刻中跨时辰 |
|---|---|---|
| 喀什 | −176 分 | **100%** |
| 乌鲁木齐 | −130 分 | **100%** |
| 拉萨 | −116 分 | **100%** |
| 昆明 | −69 分 | 75% |
| 成都 | −64 分 | 75% |
| 重庆 | −54 分 | 50% |
| 纽约 | −56 分（夏令） | 50% |
| 哈尔滨 | +26 分 | 0% |

> **乌鲁木齐 / 拉萨 / 喀什出生的用户【每一次】都拿到矛盾的盘与运限。**

**注意**：这不是"边缘少数" —— **中国西部几个大城市全部 100% 触发**。

# 四、根因

**同一个对象被构建两次，且两次的输入不同。**

这与「子时换日」的四柱矛盾**是同一个类**：

| 缺陷 | 两条路径 | 不一致之处 |
|---|---|---|
| 子时换日（已修） | `getDay()` vs `getTime()` | 换日约定不同 |
| **本缺陷** | `paipanZiwei` vs `analyzeZiwei` | **输入不同（校正 vs 原始）** |

**共同点**：**同一份输入被两条代码路径分别加工，两条路径没有共用同一个事实源。**

> 这也说明：**缺陷 32（日柱/时柱）不是孤例，而是一个"类"的第一个成员。**
> 本轮正是按 §8.5「改核心逻辑前先列出全部调用入口」去扫，才扫出第二个。

---

# 五、修法：把「构建参数」做成单一事实源（§8.5.1）

```ts
// ZwChart 增加两个字段：本轮构建 iztro 盘所用的【最终参数】
export interface ZwChart {
  …
  /** ★ 构建 iztro 盘所用的公历日期（已含真太阳时校正 ＋ 晚子时推进） */
  ziweiDateStr: string
  /** ★ 构建 iztro 盘所用的时辰索引（0=子时） */
  ziweiTimeIndex: number
}
```

- **入口一**：算出 `dateStr` / `timeIndex` 后**存进返回的 ZwChart**
- **入口二**：**改读 `chart.ziweiDateStr` / `chart.ziweiTimeIndex`**，不再从 `chart.input` 推导
- **并在入口二加注释**（§8.4.4）：
  > 「★ 禁止从 chart.input 重新推导 —— 那是原始未校正值，
  > 曾导致返回的盘与运限所用的盘不是同一个（见 P0 报告）。」

**为什么存两个原始值而不是存整个 astrolabe 对象**：后者是库对象，
放进返回体会让响应体膨胀，且耦合 iztro 的内部结构。存两个原始参数最小且够用 ✓

# 六、必须加的守护断言（§8.5 / §8.5.1）

**光修不加断言，下一个人还会写回 `chart.input`。**

```
断言：对带真太阳时偏移、且校正跨时辰的时刻：
  analyzeZiwei(chart) 所用的盘  ≡  chart 本身
（可通过暴露 ziweiDateStr/ziweiTimeIndex 后比对，或比对运限的宫位来源）

★ 牙口：把 analyzeZiwei 改回从 chart.input 推导 → 断言必须翻红。
   —— 这一支直接守住本缺陷不复发。
```

**建议并入本任务书的「归日一致性断言」同一个脚本**，因为它们守的是同一件事：
**多入口必须共用同一个事实源。**

# 七、为什么之前没被发现

```
① 它只在【校正跨时辰】时显形 —— 偏移小的城市（哈尔滨 +26 分）完全不触发
② 显形时也不报错 —— 盘正常显示、运限正常显示，只是两者对不上
③ 我们此前的紫微测试都以【不跨时辰】的时刻为准
④ 差异藏在【星曜】里 —— 若只比宫位干支，两者甚至相同（§8.6.5 事故 33）
```

**第 ④ 条尤其危险**：**这次如果我用弱判据去比，会得出"两盘相同"的假绿结论。**
