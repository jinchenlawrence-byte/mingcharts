# 〇、先读八条

1. **★★★ 这是用户（产品负责人）的明确拍板，不是我们的技术建议：**
   ```
   A 类【吉凶判词】→ ✅ 启用 7 档：大吉 / 吉 / 小吉 / 平 / 小凶 / 凶 / 大凶
   B 类【确定性词】→ ❌ 保留禁用：必 · 一定 · 注定
   ```

   - **流月**：红线明文「月度吉凶本就无凭」，标签只准 `较宜/一般/宜慎`
   **→ 正确做法是【新建一个类型专供大运与流年】，见 §二。**

3. **★ A 类启用 ≠ 可以写绝对化断言** ✗
   7 档是**时段的性质判词**（"这十年偏吉"），不是**承诺**（"你必然发财"）✓
   **B/C 两类仍由合规层拦截** ✓ —— 这是本任务的分界线。

4. **★★ 判词必须点名【结构依据】**（红线 §8.3-④ 原有要求，继续有效）✓

5. **★★★ 五处提示词要从判据【派生】，不再各手抄一份** ✓

# 一、用户拍板的三类拆分（本任务的核心决定）

**现状**：一条表混装三类词，性质完全不同 ✗

```ts
// ai-check.ts:4（现状）
export const FORBIDDEN_WORDS = ['大吉', '大凶', '积极进取', '突破性进展', '必', '一定', '注定']
//                             └─ A 判词 ─┘ └──── C 行动指令 ────┘ └─── B 确定性 ───┘
```

**改为三类分开（A 移出拦截，B/C 保留）**：

```ts
// src/lib/ai-check.ts —— 三类分表，语义明确

/** A 类：吉凶判词 —— ★ 用户已拍板【启用】（不再参与拦截） */
export const ENABLED_JUDGMENT_WORDS = ['大吉', '吉', '小吉', '平', '小凶', '凶', '大凶'] as const

/** B 类：确定性承诺 —— ❌ 保留禁用。占卜合法，但承诺确定结果违法（FTC 惩罚欺骗非占卜；
 *  且「禁绝对化措辞」是 App Store 合规要点）。★ 与准确率无关。 */
export const FORBIDDEN_CERTAINTY_WORDS = ['必', '一定', '注定'] as const

/** C 类：行动/投资指令 —— ❌ 保留禁用。不是命理语言而是行动建议；
 *  事故 18 的实际致害者（用户据「宜积极进取」炒股/期货暴亏）。★ 与准确率无关。 */
export const FORBIDDEN_ACTION_WORDS = ['积极进取', '突破性进展'] as const

/** 实际拦截表 = B + C（不含 A） */
export const FORBIDDEN_WORDS = [
  ...FORBIDDEN_CERTAINTY_WORDS,
  ...FORBIDDEN_ACTION_WORDS,
] as const
```

**★★ 注意「必」的既有机制**：`FORBIDDEN_WORDS` 里的 `'必'` 已可覆盖
「必然/务必/必定」✓（含字匹配）；`strictBi` 参数用于合婚口径物理禁「必」（含不必/未必）✓
**→ 这三项语义不变，不要动。**

## 3.2 ★★ `scoreToTag` 改为 `scoreToFortuneTier`

```ts
/** 大运/流年：7 档。★ 结构性缺陷封顶（事故 18 的纪律，必须保留并扩展） */
export function fortuneTierOf(score: number, structuralIssues: string[] = []): FortuneTier {
  // ★★ 有结构病者封顶：结构病越多，上限越低
  //    —— 这是事故 18 的修复（"用神到位 ≠ 用神有效"），不得删除
  const cap =
    structuralIssues.length === 0 ? 4 :      // 无结构病 → 可达「大吉」
    structuralIssues.length === 1 ? 2 :      // 1 个     → 最高「小吉」
    0                                        // ≥2 个    → 最高「平」
  const s = Math.min(score, cap)

  if (s >= 4) return '大吉'
  if (s === 3) return '吉'
  if (s === 2) return '小吉'
  if (s >= 0) return '平'          // 0 与 1 合并为「平」（正向不虚增）
  if (s === -1) return '小凶'
  if (s === -2) return '凶'
  return '大凶'                    // ≤ −3
}
```

**★★ 为什么 0 与 1 都归「平」**：
```
· 保证「平」是真正的中间档（不偏乐观）✓
· 且只有【无结构病且多个喜用同现】才够「小吉」以上 ✓
→ ★ 这会让 7 档分布自然偏中，避免"大吉"滥用 ✓（见 §五）
```

**★ 反向不设 floor** ✓ —— 结构病只封上限、不封下限（结构病本就加凶）✓
**★★ 但 §五 的断言必须检查下限侧是否被滥用**（事故 19：从"过度乐观"滑到"过度宿命"）。

# 五、★★★★ 7 档分布断言（本任务最重要的产出）

## 5.1 三条断言（全部离线、纯函数、可进 verify）

```
① ★★ 死档检测
   在 N 个真实命盘（取 mingli-cases.json 的 2403 条中的样本，或固定测试集）
   × 每盘全部大运步（约 8–10 步）的样本上：
   断言 7 档【每一档都至少出现过一次】
   → 若某档恒为 0 ✗：该档判定写错了（阈值不可达）✓

② ★★★ 滥用检测（防止"大吉"泛滥）
   断言【大吉 + 大凶 合计占比 ≤ 阈值】（建议先测出实际值，再定阈值）
   ★ 依据：事故 18 的教训是"乐观档给得太满"✓

   → 所以【上下两侧都要设上限】✓（不是只压乐观侧）

③ ★★★ 反向偏向检测（红线 §8.3-③ 直达）
   断言【正向档（大吉+吉+小吉）占比】与【负向档（小凶+凶+大凶）占比】
   两者之差不超过某阈值
```

**★★ 输出的必须是【真实分布数字】**（不要只打印"通过"）✓
