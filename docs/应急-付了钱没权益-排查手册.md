# 应急：用户说「付了钱但没权益」怎么查

> 适用场景：用户来信说已经付款，但报告没解锁 / 会员没生效。
> 阅读者不需要看代码。**按顺序做，前三步能解决绝大多数情况，第四步才是人工补。**
>
> 前置常识：我们的付款由 Waffo 托管收银台完成，支付成功后 Waffo 会向我们的接口发一条通知（webhook），
> 我们收到后把流水写进数据库，权益才生效。所以问题一定出在「钱收了」和「权益发了」之间。

---

## 第 0 步：先确认钱真的收到了（30 秒）

**去哪看**：Waffo Dashboard → 左侧 **Payments**

**怎么找**：用用户的邮箱搜索；或按日期 + 金额找

**看什么**：

| 字段 | 你要看到的值 | 说明 |
|---|---|---|
| Status | **Paid** | 只有 Paid 才是真收到钱 |
| Amount Paid | 与商品价格一致 | 注意可能显示为当地货币（如 JPY），不是美元 |
| Payment ID | `PAY_` 开头 | **记下来，后面每一步都要用** |
| Customer | 用户邮箱 | 与来信邮箱核对 |
| Description | 商品名 | 确认买的是哪一份报告 |

- 如果 Status 是 **Pending / Declined / Failed / Disputed**：不是「掉权益」，是这笔根本没付成功。直接告诉用户重新下单/换支付方式，**不要补权益**。
- 如果是 **Refunded**：用户已退款，权益本就应该没有，**不要补**。

**同时记下订单号**：点开该笔 → 找 **Metadata / orderMerchantExternalId**，形如 `MC-<用户ID>-<13位数字>`。
后面第 1 步要把它拼进链接。

---

## 第 1 步：让用户重开「支付成功页」（自愈，通常 30 秒）

这一页会自动对账补写，**是最快、最安全的一步**，先做这个。

**发给用户的链接**（把 `<订单号>` 换成第 0 步记下的 `MC-...`）：

- 简体：`https://www.mingcharts.com/checkout/success?ref=<订单号>`
- 繁体：`https://www.mingcharts.com/tw/checkout/success?ref=<订单号>`
- 英文：`https://www.mingcharts.com/en/checkout/success?ref=<订单号>`

**让用户**：打开链接 → 等 30 秒 → 刷新一次 → 再去看报告/会员。

**这一页在背后做什么**（不用向用户解释）：先轮询权益，仍没有就调用对账接口，向 Waffo 反查这笔付款并补写流水。

**成功标志**：

1. 用户那边报告能打开了；或
2. Supabase → Table Editor → `payments` 表里出现这条 `transaction_id = PAY_...` 的记录，`status = paid`。

**没成功** → 进第 2 步。

---

## 第 2 步：让用户登录后打开对应页面（补写兜底）

有些页面在「解锁回写」时也会补插流水。

**让用户**：登录 → 打开「我的报告」（命书在「我的命盘」）→ 点开对应那一份 → 刷新。

**成功标志**：同第 1 步（报告能看 / 数据库出现流水）。

**没成功** → 进第 3 步。

---

## 第 3 步：查 Waffo 的 webhook 投递日志（看是不是通知失败了）

如果第 1、2 步都没补上，基本可以确定是**通知没处理成功**，这一步能看到确切原因，还能一键重发。

**去哪看**：Waffo Dashboard → **Developers** → **Webhooks** → 选中我们的 endpoint → **Deliveries / Logs**（投递记录）

**怎么找**：用第 0 步的 `PAY_...` 或订单号 `MC-...` 搜索；也可以按时间找用户付款那一刻。

**看什么**：

| 字段 | 常见值 | 含义 |
|---|---|---|
| Status | `success` | 通知已成功处理，问题不在通知，回到第 4 步查权益归属 |
| Status | **`failed`** | 通知处理失败，**这是我们要找的** |
| HTTP status | **500** | 我们服务端报错（常见是写库失败） |
| Response | 含 `payments 写入失败: 23514` | 数据库约束拒绝了这条流水 |

**怎么修**：确认第 4 步开头的「数据库约束」已经执行过 → 在该条投递上点 **Resend（重发）**。

> 重发会完整重跑一遍，不会因为「已处理过」被跳过。
> **注意时间窗**：我们的接口只接受 **45 分钟内**的通知，超过 45 分钟的重发会被拒绝（返回 401）。超过就只能走第 4 步。

**成功标志**：该条投递变为 `success`，且用户报告可用。

**没成功** → 进第 4 步。

---

## 第 4 步：人工补录（最后手段）

> 做之前必须确认两件事，否则补了也没用、甚至报错。

### 4.1 先确认数据库约束已更新（一次性，做过就跳过）

Supabase → **SQL Editor** 执行（可重复执行）：

```sql
ALTER TABLE payments DROP CONSTRAINT IF EXISTS payments_payment_method_check;
ALTER TABLE payments ADD CONSTRAINT payments_payment_method_check
  CHECK (payment_method IN ('card', 'applepay', 'googlepay', 'wechat', 'alipay', 'stripe'));
```

验证（只读）：

```sql
select conname, pg_get_constraintdef(oid) as def
from pg_constraint
where conrelid = 'public.payments'::regclass
  and conname = 'payments_payment_method_check';
```

`def` 里必须同时含 `applepay` 和 `googlepay`。没有就先停下，别继续。

### 4.2 查这笔到底有没有落库

Supabase → **SQL Editor**：

```sql
select id, user_id, amount, sku, payment_type, payment_method, status, transaction_id,
       order_merchant_external_id, paid_at
from payments
where transaction_id = 'PAY_这里换成真实ID';
```

- 查到且 `status='paid'` → 钱和流水都在，**问题在权益归属**（多半是 `user_id` 对不上），不要重复插入，查 `user_id` 是否等于用户真实账号 ID。
- 查不到 → 进 4.3 补插。

### 4.3 补插一次性报告流水

从第 0 步拿 `PAY_...`、订单号、金额、用户 ID；从商品名确定 `sku`（取值见 `src/lib/pricing.ts` 的 SkuId，如 `fatebook` / `ziwei_deep` / `hemun` / `geo` / `annual_report`）。

```sql
insert into payments (user_id, amount, sku, payment_type, payment_method, status,
                      transaction_id, order_merchant_external_id, paid_at)
values ('<用户UUID>', <金额>, '<sku>', 'single', 'card', 'paid',
        'PAY_...', 'MC-...', now())
on conflict (transaction_id) do nothing;
```

`payment_method` 填第 0 步看到的支付方式：`card` / `applepay` / `googlepay`。

### 4.4 会员没生效时

会员状态存在 `profiles` 表（不是 `payments`）：

```sql
update profiles
set is_member = true,
    member_plan = 'monthly',            -- 或 'yearly'
    member_expire_at = now() + interval '1 month',  -- 年费改成 1 year
    member_order_id = 'PAY_...',
    member_auto_renew = true
where id = '<用户UUID>';
```

### 4.5 收尾

让用户**退出重新登录**（或刷新），再看报告/会员。
然后在工单/邮件里回复用户，并记录本次处理（见第 5 步）。

| 日期 | 用户邮箱 | Payment ID | 订单号 | 卡在哪一步 | 处理动作 | 是否恢复 |
|---|---|---|---|---|---|---|
|  |  | PAY_ | MC- |  |  |  |

## 禁止事项

1. **不要**在没确认 `Status = Paid` 之前补权益。
2. **不要**手工改已有流水的 `transaction_id`（它是唯一键，改了就重复/错乱）。
3. **不要**为了「测试约束」往 `payments` 表里插测试数据——会污染账务，也可能误发权益。
4. **不要**跳过第 1、2 步直接人工补，能自愈的先自愈，人工补是最后手段。
5. **不要**在 45 分钟验签窗外指望 webhook 重发能成功。

---

## 一句话流程图

```
用户说没权益
  → Waffo Payments 确认 Paid（否则让他重下单）
  → 发成功页链接让他重开（自愈）
  → 仍不行：让他登录后打开报告页（兜底回写）
  → 仍不行：Waffo Webhook logs 找 failed → Resend
  → 仍不行：Supabase 补插 payments / 改 profiles
```
