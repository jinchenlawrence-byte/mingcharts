# 命理项目 · 验收标准与红线（总纲）

> **性质**：本项目所有数据工作与模块开发的**统一质控基准**。
> 后续任何交接书**只需引用本文档**，不必重复抄写纪律条款。
  —— ★ 「确认注入有效」失败 ⇒ 【立即中止】，不跑断言（否则红是不知情的）
>
> **适用对象**：DeepSeek 侧（规格与审核）· TraeCode 侧（执行与实现）
>
> **维护规则**：每次协作中**新撞出来的教训，必须回写进本文档**，否则下一轮会重犯。
> 本文档的每一条都对应一次真实事故（见 §十一 事故档案）。
>
> **两条写规则的强制要求**（详见 §〇.1）：
> 1. **没有事故支撑的规则不要加**
> 2. **每条规则必须写明「什么情况下不适用」**——只写适用、不写边界，就是下一个坑的种子

# 〇、怎么用这份文档

| 场景 | 用法 |
|---|---|
| 写交接书 | 开头写一句「纪律见《验收标准与红线》§一～§五」，然后**只写本轮的规格** |
| 验收交付 | 逐条对照 §二（校验）与 §五（分级），不合格不通过 |
| 出现分歧 | 以本文档为准，不以"上次是这么做的"为准 |
| 新增规则 | 追到 §十一 写明**事故经过**，再在正文加条款。**没有事故支撑的规则不要加** |

## 〇.1 ★ 维护原则：每条规则必须写明「不适用的情况」

**这是写规则时的强制要求，与「没有事故支撑的规则不要加」并列。**

> **一条规则若只写"适用时怎么办"，不写"什么情况下不适用"，
> 就会在下一个相似但不同的场景里被误用——而且误用者会以为自己遵守了规则。**

**每条新规则必须写出三部分：**

```
① 适用对象      —— 这条规则管的是什么（哪类模型／哪类结论／哪类数据）
② 适用条件      —— 满足什么才该套用
③ ★ 不适用的情况 —— 什么情况下套用它是错的，以及为什么
```

**为什么这条原则是被事实验证过的**：

| 事故 | 规则 | 漏写「不适用」，后果 |
|---|---|---|
| **21** | §8.4「单一类别占比 >50% → 区分度不足」 | **未限定**「仅适用于固有属性模型」→ 被套用到**相对关系**模型上 → 把"观察点的地理事实"误判为"模型缺陷"，要求补 200 座城（**且补了也没用**） |
| **15** | 「验收指标必须唯一确定」 | 缘于更早一条"用期望值验收"，同样因为**没写清期望值在多解场景下不成立** |

**两个反例的共同点**：

> 规则本身在**它原本的场景里是对的**——错的是**边界没画出来**。
> 而规则越积越多时，**没有边界的规则就是下一个坑的种子。**

**做法上的具体要求**：

1. **写正文条款时，紧跟一条「⚠️ 不适用」**（可参考 §8.4.1 的适用域表写法）
2. **交接书里引用某条规则时，须同时抄上它的不适用条件**——只抄适用部分等于没抄
3. **若一时想不出不适用的情况，就在条款里写「暂未发现不适用场景」**
   ——**显式留白**比默认省略好：它标明"这里没想过"，而不是"这里不需要想"

# 一、四条红线

> 这四条**不可交易**。任何"为了进度/为了数量/为了好看"的理由都不能突破。

## 红线 1 · 不得编造

**禁止**产出任何"看起来合理但无来源"的内容。

**具体表现**（都真实发生过）：
- LLM 对坏 OCR 拼凑出**合法但不存在的四柱**（能过 60 甲子校验）
- 笔记里出现**底部文本 0 命中的"OCR 原句"**（如「身衰用印最良」「英雄独压万人」）
- 整节内容是**凭印象写的**（《渊海子平》笔记里 14 类神煞起法全部零匹配）

**判断标准**：**任何一句被标为"来源"的话，必须能在指定底本中检出。**

## 红线 2 · 不静默改字

发现底本讹误、异文、OCR 疑误——**保留原字 + 标注**，**不得替古籍改字**。

**范例**（正确处置）：
> 《三命通会》卷八 page133 原文作「丙辰日**乙**丑時」。
> 五鼠遁下丙日只能是己丑时；经**渲染原页放大肉眼确认**字确为「乙」，
> 且殆知阁本同样作「乙」，而全书其余 5 个丙日小节均作「己丑」。
> → 判定为文渊阁本**刊刻讹误**，**如实保留、标 `可用:false`、单列待校**。

**OCR 形近字**同理：保留原字，另加 `OCR疑似形近: "已→己"` 字段提示。

## 红线 3 · 自创体系必须声明

**自己推演出来的东西，必须标明是自己推演的，不能冒充古籍。**

**反例**：地理模块给 86 座城市标注五行，`reason` 写「厚土载物」「政金肃敛」，
**无一条引古籍**，却直接参与打分（"主气合目标 +28"）并呈现给用户。

**正例**：笔记中区分
- `【原文】` —— 古籍原话（带底本行号）
- `【本笔记·工程化设定】` —— 整理者归纳（如优先级、决策树）
- `【存疑】` —— 查不到出处

## 红线 4 · 不得为数字好看而妥协

- ❌ 为了保住记录数而放宽门槛
- ❌ 为了"通过率好看"而删记录或改干支
- ❌ 在 `person`/`人物` 拿不准时硬填
- ✅ **数据规模下降是预期且正确的**

**范例**：三命通会命例表提取，曾实现"跨列配对"得到 874–1568 条"看似完整"的命例、
历法通过率 >99% —— 但回图发现会**张冠李戴**，**主动撤销**，最终只交 100 条完整四柱。
**这是本项目最正确的一次决定。**

# 二、五道校验（全部是可复算的硬规则）

> **原则**：判据必须是**确定性规则**，**不得使用"凭知识估计的期望值"**。
> （曾发生：用未溯源的人物生年去判别人数据存疑，逻辑不自洽。）

> **原则（补充）**：**验收指标必须唯一确定。**
> 凡"正确答案不唯一"的场景（多来源解读、多版本异文等），**不得用单一样本值作验收标尺**，
> 应改用**可复算的结构性指标**（如"某类条目数 = 0"、"双通过率 ≥ X%"）。
> （曾发生：把"多个合法答案中的一个"写成"期望值"，导致正确交付被判"未命中"——见 §十一 事故 15。）

## 校验 1 · 60 甲子合法性

```
合法干支 ⟺ (天干序 % 2) === (地支序 % 2)
```
即阳干配阳支、阴干配阴支。

**作用**：拦掉"甲丑""乙子"这类根本不存在的干支组合。
**局限**：**拦不住幻觉** —— LLM 拼出的四柱天然满足此规则。

## 校验 2 · 五虎遁（月干 ← 年干）

```python
GAN='甲乙丙丁戊己庚辛壬癸'; ZHI='子丑寅卯辰巳午未申酉戌亥'
gi=GAN.index; zi=ZHI.index

def wuhu_ok(nian_gz, yue_gz):
    s = (gi(nian_gz[0]) % 5) * 2 + 2            # 寅月起月干
    o = (zi(yue_gz[1]) - 2 + 12) % 12 + 1       # 寅=1 .. 丑=12
    return GAN[(s + o - 1) % 10] == yue_gz[0]
```

口诀：甲己之年丙作首，乙庚之岁戊为头，丙辛必定寻庚起，丁壬壬位顺行流，戊癸甲寅好追求。

## 校验 3 · 五鼠遁（时干 ← 日干）

```python
def wushu_ok(ri_gz, shi_gz):
    s = (gi(ri_gz[0]) % 5) * 2                  # 子时起时干
    return GAN[(s + zi(shi_gz[1])) % 10] == shi_gz[0]
```

口诀：甲己还加甲，乙庚丙作初，丙辛从戊起，丁壬庚子居，戊癸壬子是真途。

> **校验 2+3 合称「历法双校验」。任何真实八字都必须同时满足。**
> **工具**：`scripts/cases/audit-calendar.js`（Node，全库批量审计）

## 校验 4 · 溯源校验（防 LLM 幻觉）

**规则**：LLM 给出的四柱 8 字，**必须依次连续出现在源文本中**（归一化去标点空白后）。
否则判为幻觉，**丢弃**。

**实测效果**（千里命稿同一批 15 块）：

| 校验策略 | 通过 | 丢弃 |
|---|---|---|
| 仅 60 甲子 | 7 | 0 |
| **加溯源校验后** | **0** | **10** |

**工具**：`scripts/cases/extract-with-llm.js` 的 `groundCheck()`
**⚠️ 局限**：**表格版式下会失效**（见 §三.2）。

## 校验 5 · 回图 / 回源核对

凡**跨块、跨列、跨页拼装**的记录，除历法校验外**必须另有归属证据**
（同小节 id、`bbox_2d` 邻接证明、或人工回图）。

**工具**：`scripts/cases/probe-pdf-textlayer.py`、PyMuPDF 裁图 + 视觉核对。

# 三、校验的边界（★ 最重要的一节）

> **不理解这三条边界，校验就会从"质控"变成"自欺"。**

## 3.1 历法校验：防柱子错位，**防不住张冠李戴**

五虎遁只约束「年与月之间的关系」，五鼠遁只约束「日与时之间的关系」，
**它们不约束「某个干支属于哪一条命例」。**

**实例**（三命通会卷八 page13）：把不同小节的两列强行配对，得到
「年乙亥 月丁亥 日甲申 时乙丑」—— **五虎遁✓ 五鼠遁✓，但人物与日柱全错**。

> **结论**：`历法校验通过` 是**必要条件，不是充分条件**。

## 3.2 溯源校验：在**表格版式**下失效

四柱在文本流里**不连续**（天干地支分列在不同 bbox），此时字符串匹配会**误杀真数据**。

**处置**：表格类底本改用**回图核对**（§校验 5）。
**实例**：三命通会命例表 604 页扫描本，靠 `bbox_2d` 几何 + 历法双校验，
最终得 98 条完整四柱、6278 条三柱。

## 3.3 「人物/应验齐全」≠「四柱正确」

**两个维度必须分开。**
**实例**：`cases-web-gist.jsonl` 曾按"有人物+有应验"选为「精选」，
实测历法双通过率**仅 86.8%**。

## 3.4 附带结论：古籍的「命例表」常常**只记年柱**

《三命通会》卷八/九的时断命例表，**分列型命例本就省略月柱**
（每列只写"年干支 + 人物 + 官衔"）。
→ **这不是算法没做好，是源数据只给了这些。** 强行跨列补月柱即违反红线 1。

# 四、标注与溯源规范

## 4.1 三级标注（强制）

| 标注 | 含义 | 要求 |
|---|---|---|
| `【原文】` | 古籍原话 | **必须检索确认存在**，引用须带**底本行号** |
| `【本笔记·工程化设定】` | 整理者归纳（优先级、决策树、评分等） | **必须显式标明非原文** |
| `【存疑】` | 查不到出处 | 如实写「本次语料未见」，**不许用近义句冒充原文** |

## 4.2 引用格式

```
〔原文〕"……"（《三命通会》·<篇名>，底本行 N）
〔原文〕"……"（《千里命稿》·<篇名>，底本行 N）
```

## 4.3 字段级标注（数据集）

- `可用` —— **只能有一个含义**：`四柱俱全 && 五虎遁 && 五鼠遁`
  （历史遗留的其他含义须迁移到 `原可用` 字段保留）
- `非命例: true` —— **无论历法是否通过，一律不得进入任何交付物**
- `质量等级` —— A/B/C（定义见 §五）
- `历法校验` —— `{五虎遁, 五鼠遁, 双通过, 备注}`
- `OCR疑似形近` —— 提示而不改字

# 五、数据质量分级与打包规范

## 5.1 文件级分级（按历法双通过率）

| 等级 | 双通过率 | 含义 |
|---|---|---|
| **A** | ≥ 99% | 可放心使用 |
| **B** | 90% – 99% | 逐条核对后可用；不过者须单列 |
| **C** | < 90% | 须重做或标废；**不得作为主要数据源** |

## 5.2 记录级分层（按四柱完整度）

| 分层 | 可用范围 |
|---|---|
| **完整四柱** | 可作格局 / 调候 / 月令分析 |
| **三柱（缺月柱）** | **仅**可用于年/日/时相关分析；月柱缺失会**直接废掉月令格局与调候判断**，勿混用 |
| **仅年柱** | 仅供人物-功名-年柱的粗关联统计，**不可作八字分析** |

## 5.3 打包规范（面向用户的产品数据）

**必须满足全部**：

1. **只从 A 级 + B 级文件构建**（C 级一律不进用户库）
2. **排除聚合文件**（`cases-all` / `cases-web-all` / `cases-prime` 等并集文件）
3. **排除 `非命例` 文件与记录**
4. **排除已被取代的文件**（如 v1 被 v2 取代后，v1 不得再打包）
5. **去重按「文件质量等级」取优**，**不得以「文本更长」为择优标准**
   （更长 ≠ 更对；曾发生错误的长文本覆盖干净短文本）
6. 加**文本质量门槛**（长度下限 + 剔除残句特征）
7. 加 `person` 噪声过滤（功名词、截断碎片不得当人名）

## 5.4 打包后自测（硬指标）

| # | 指标 | 期望 |
|---|---|---|
| 1 | 来自已标废文件的条目 | **0** |
| 2 | 以标点开头的 `text`（`^[，。、；：]`） | **0** |
| 3 | `text` 过短的条目 | 显著下降 |
| 4 | 用户库**历法双通过率** | **≥ 99.5%** |
| 5 | 来源只来自 A/B 级文件 | ✓ |

## 5.5 去重原则：多来源解读须保留为多值

**同一条命例（同一四柱）在源库中常有多个来源、多个流派的解读。不得去重成一条。**

**实测规模**（2026-10 全库）：

```
候选四柱 2503  |  断语总数 5296
按四柱去重后只保留 2503 条  →  丢弃 2793 条（53%）
其中 66% 的四柱有 ≥2 个不同断语，最多者 12 个
```

**实例**（阎锡山 `癸未 辛酉 乙酉 丁亥`，共 6 条断语、来自 4 本书）：

| 书 | 断语 | 角度 |
|---|---|---|
| 《穷通宝鉴》徐乐吾注 | 支聚两酉，辛金出干，喜癸丁并透，行南方火运 | **调候** |
| 《子平真诠评注》 | 乙木只要有印通根，不怕身弱，煞透有制，即为贵格 | **格局** |
| 《千里命稿》韦千里 | 秋木凋零…杀重身轻…制化之功乃完备矣 | **综合批断** |

**三派读同一张盘、角度各异——这正是本 skill 核心卖点「分流取用」的活教材。
去重成一条等于把最有价值的部分丢掉。**

**正确做法**：

```js
// ✗ 错：按四柱去重，只留一条
{ year, month, day, hour, text, source }

// ✓ 对：按四柱归并，保留全部解读
{ year, month, day, hour, readings: [{ source, text, person }] }
```

**去重只应剔除「同来源、同文本」的重复项**，不得跨来源合并。

## 5.6 数据与代码分离：特例数据须独立成文件

**凡「抢救」「手工修正」「个案补录」一类**的**特例数据**，
**必须写成独立的数据文件**（与其他命例同构，放 `references/cases/`），
**不得硬编码进构建脚本**。

**为什么**（有具体事故，见 §十一 事故 17）：

```
✗ 错：把抢救数据硬编码在 build-mingli-cases.mjs 里
   → 这 2 条不在命例库中：不进 index.json、不参与质量分级、审计时看不见

✓ 对：新建一个抢救数据文件（与其他命例同构，放 references/cases/，
      建议命名 cases-salvaged.jsonl），脚本按普通文件读取
   → 自动享受 readings 聚合、质量分级、索引登记、可被审计
```

> 注：上述 `cases-salvaged.jsonl` 为**建议新建的目标路径**，当前尚未创建。

**判据**：**能被审计看见的，才算进了库。**
一条数据如果不在 `references/cases/` 里，它在制度上就"不存在"——
即使它确实出现在了产品里。

**同时**：特例数据的 `来源` 字段须填**真实出处**，不得沿用已标废的书名
（否则会被 `SKIP_BOOKS` 类黑名单再次剔除）。

# 六、版本与底本意识

## 6.1 铁律：同名书不同版本，价值可能完全不同

**先做版本比对**（体量、题名、是否含评注/命例），**再决定用哪本**。

## 6.2 已发现的版本陷阱

| 书 | 陷阱 |
|---|---|
| 《三命通会》 | 本地 PDF 是**现代简化排印本**（带白话释意），**把全部命例表删光了**；命例表只在四库本里 |
| 《穷通宝鉴》 | 殆知阁本 = **余春台原文**（3.4 万字，仅正文）；旧笔记所据 = **造化元钥评注**（22.8 万字，徐乐吾评注 + 数百命例）。**两者不可互校** |
| 《渊海子平》 | `_ocr/` 本是坏 OCR；`_web/` 是殆知阁干净本 |
| 《子平真诠评注》 | `_ocr/` 本实为**内容更全的民国排印全本**（含方重审序、徐自序、近人命例），但**字序错乱**，只能作行号旁证、**不可作文字依据** |

## 6.3 底本目录约定

| 目录 | 性质 | 可用工具 |
|---|---|---|
| `命理书籍\_web\` | **干净在线校对文本**（殆知阁 / 维基文库） | `extract-clean.js`、`extract-with-llm.js` |

# 八、两个域的不同标准

> **数据开采**与**功能开发**的风险点不同，验收标准也不同。

## 8.1 数据开采域（命例库、笔记校订）

**成功标准**：**每条数据都能回源核对，且不掺一条编造的。**
**数量少不是失败，掺假才是失败。**
- 主要工具：五虎遁/五鼠遁、溯源校验、回图核对
- 交付物：`references/cases/*.jsonl` + 核验表
- 验收：§二 五道校验 + §五 分级

## 8.2 功能开发域（合婚、地理、排盘等）

**架构铁律**：**规则引擎定事实 → AI 只做解读**
- AI **只引用规则引擎产出的事实**，不自行推演干支关系
- AI prompt 须有**兜底文案**
- **术语纪律**：五行相克不称"冲"；透干/藏干定义须准确；藏干逐字引用

**呈现纪律**：
- **分数不要给太满**（曾出现基础分 60，导致评级普遍偏高、"上等良缘"易得）
- **自创体系必须显式声明**（如"城市五行取象为本产品设定，非古籍原文依据"）
- **付费墙默认关闭**，须用户明确要求才加

## 8.3 判定纪律（时段类结论专用）

> 适用于**大运／流年／流月**等"分时段给出吉凶倾向"的功能。

**① 时段维度的判据，必须依赖该时段。**

若某个"大运维度"的结论对**全部大运**都相同，那它是**命局常量**，不是大运判定。
—— 应移到「命局总论」说一次，**不得**以「大运判定」的形式重复 N 遍。

**自检方法**：统计该维度在各时段上的**去重取值数**。

```
去重数 / 总时段数  接近 1/N → 无区分度，判据写错了
```

**② 纯原局条件不得作为时段判定的主条件。**

原局特征（如"比劫林立＋财星深藏"）对每一步大运恒真，
若用它做前置判断，会**短路**掉下游真正依赖大运的分支。

**③ 修一个偏向时，必须检查是否引入了反向偏向。**

同一个错误可以有两个方向：把该守说成该攻（**过度乐观**），
或把所有人说成一辈子没戏（**过度宿命**）——**两者都是错误信息**。
修完必须回头验一遍：结论是否从"过度乐观"滑到了"过度悲观"。

**④ 严禁输出「大吉／大凶」类绝对标签。**

大运段一律用**分维度（事业/财运/健康/六亲）+ 吉/平/滞 + 具体措辞**；
流月只用「较宜／一般／宜慎」。且**措辞须点名结构**（被合/被冲/被化/被夺/深藏/孤立），
不得只说结论不说依据。

**⑤ 依据等级为「产品设定」的维度，不得与典籍维度等权参与总评。**

自创指标与典籍判据等权，等于**等价呈现**（违反红线 3 的精神）。
产品设定维度**照常展示**（有参考价值），但不进 `overall`／总分计算，
或在卡片上标注"仅示当前节奏，不参与总评"。

## 8.4 分类模型的分布检验

> 凡给对象贴**分类标签**的模型（城市五行、格局类型、档次分级等），
> **必须先做分布检验**——否则会出现"某个类别永远取不到"的功能性缺陷。

### 8.4.1 两条硬指标（**须先分清模型是"固有"还是"相对"**）

```
① 任一类别计数 = 0   → 模型不适用（某些用户会取不到候选）      ← 两类模型都适用
② 单一类别占比 > 50% → 区分度不足（标签形同虚设）              ← ⚠️ 仅适用于「固有属性」模型
```

**⚠️ 规则 ② 有适用域限制（此处曾出错，见事故 21）：**

| 模型类型 | 规则 ② 是否适用 | 理由 |
|---|---|---|
| **固有属性**（对象自身标签） | ✅ **适用** | 分布由构造决定；某值占 62% 说明标签**真的**没区分度 |
| **相对关系**（依赖观察点实时算） | ❌ **不适用** | 分布是**观察点的地理/结构事实**，不是模型缺陷 |

**实例对照**：

| | 旧模型（城市五行＝固有属性） | 新模型（方位五行＝相对命主） |
|---|---|---|
| 某五行占比高 | 木 62% —— **构造 artifact**，标签形同虚设 → **该判 ✗** | 乌鲁木齐 77% 东 —— **真实地理事实** → **不该判** |

### 8.4.2 相对关系模型：改用「操作性判据」

**对"相对某中心"的量，原始池分布必然随观察点变化。真正的判据是：**

```
★ 每个目标类别的可用候选数 ≥ Top-N
   即：用户实际能拿到每一类的推荐
```

**这才是规则 ② 「标签形同虚设」的本意** ——
标签有没有用，要看**用户实际能不能拿到每类推荐**，不是看池子里有多少。

**并且：缺口若源于结构（方位扇区宽窄不一），要改的是「扇区宽度」，不是「数据量」。**
（补数据解决不了结构性稀疏，见事故 21。）

### 8.4.3 根因的思维错误（值得记住）

**已发生的实例**（见事故 20）：城市五行用"相对中国地理中心的方位"判定，
结果 **木 62% / 水 0 城** —— 喜用含水的命主**永远推荐不出水城市**。

> **「方位五行」是「方位对某个人的影响」，不是「对象相对某原点的固有属性」。**
>
> 混淆这两者，就会把"相对"的量当成"绝对"的属性来用，
> 而任何"相对某中心"的量，在**中心周围分布不均**的对象集上必然退化。

**正确的区分**：

| 概念 | 性质 | 例子 |
|---|---|---|
| **对象固有属性** | 绝对，可预先标注 | 城市的地气（地理/物产） |
| **相对关系** | 相对，须按用户实时计算 | 城市相对**命主出生地**的方位 |

### 8.4.4 ★ 标签与判据分离时，必须显式说明二者关系

> **当"标签的划分标准"与"判据的划分标准"不同时，
> 同一对象可能「标签属 A、判据属 B」。**
> **这不是 bug，但必须并列展示 + 一句说明**——否则用户会认为是矛盾。

**实例**（城市方位）：

| | 划分 | 标准来源 | 用途 |
|---|---|---|---|
| **卦位** | 8 等分（各 45°） | 传统八卦 | **方位标签**（"东南·巽木"） |
| **门控** | 5 类（四正各 84°，四维各 6°） | 服务"每类可取满"的操作需求 | **五行判定** |

**→ 同一城市可能「卦位属土、门控属木」。**

**若只显示其中一个，就是误导**：用户看到"东北·艮土"却被归入"木之地"，会认为产品自相矛盾。

**处置要求**：

1. **并列展示**两套结果（标签 + 判据）
2. **加一句说明**为什么两者可能不同（划分标准不同）
3. **文档化**：把这种分离写成**刻意的设计决定**，避免后续被当成 bug 提回

**为何要写进总纲而不只写产品文档**：
这条原则**通用于任何"标签体系 ≠ 判据体系"的场景**
（如格局名 vs 取用判据、神煞名 vs 吉凶判据），不是城市方位独有的问题。

### 8.4.5 ★ 模式匹配式检查必须处理「否定式」

> 用关键词/正则检查合规性时，**必须区分「肯定」与「否定」**。
> 否则**正确的表述反而会被判为违规**。

**实例**（收尾轮 AI 合规抽验）：检查"是否把产品设定维度说成典籍"的正则，
只判断`同句是否同时出现「典籍」与「大运同步」`，结果把这句话判为违规：

> "此为大运同步的**产品设定**参考指标，仅作节奏参考，**非命理典籍所载**"

**这句话恰恰是正确表述**——它明确**否认**了典籍归属。

**要求**：

```
检查「A 与 B 不得同句并列」时，须排除否定式：
  非…典籍 ｜ 不是典籍 ｜ 并非典籍 ｜ 非…所载
```

**推广**：凡"禁止某组合出现"的检查，都要先问一句
**「如果模型正确地否定这个组合，会不会被误伤？」**

### 8.4.5.1 ★ 升级：「归属断言」优于「邻近否定」（**本条的最终形态**）

> **要判"有没有把 A 说成属于 B"，就应直接检测"归属"这个语义关系，
> 而不是退而求其次检测"两词挨得近不近 + 有没有否定词"。**

**为什么"邻近否定"不够**（我方规格曾在此出错，见事故 25）：
它只覆盖"肯定 vs 否定"两类，**漏掉第三类——"只是并列分级，根本不存在归属断言"**：

```
「三者依据等级不同：干支生克为典籍所重，纳音为唐宋古法之遗，生肖则为民间俗论」
  「邻近否定」→ 误报 FAIL ✗（同句共现且无否定）
  「归属断言」→ INFO ✓（压根没有"生肖属于典籍"的断言）
```

**而这句话恰恰是依据分级的"标准写法"。**

**最终判据（检测归属，而非邻近）**：

```
方向一：混淆词 → 归属词（源自/出自/依据/为/乃/与…）→ 典籍（所载）
方向二：典籍 → 有明训/明载/载有/论及…（断言典籍支持混淆词）
窗口不跨 。；！，、  —— 逗号/顿号前后通常是不同主语的并列分级
归属词前紧邻否定（非/不是/并非/无/未…）→ INFO 留痕，不判失败
```

**方法论**：**先问"我要判的语义关系是什么"，再设计匹配式**；
不要一上来就用"词距 + 否定"做近似。

### 8.4.6 AI 输出的验收本质是「抽样」

> **单次 PASS 不构成稳定保证。** AI 输出是非确定性的——
> 同一份代码，两次运行可能一次通过、一次触发误报。

**含义**：

1. **固定多个用例**（建议 ≥3 个），而非只跑 1 个
2. 在脚本输出与结论中**注明"单次抽样"**性质，不得表述为"已保证合规"
3. **周期性"假红"会消磨对检查的信任** —— 因此检查脚本自身的**误报率**，
   与它能不能查出问题**同等重要**

### 8.4.6.1 ★ 抽样原则**同样约束规格方的结论表述**

> **推论必须限定在证据范围内。**
> 本原则不只是"测试脚本的注意事项"——**它首先约束写结论的人。**

**已发生的实例**（事故 26）：DeepSeek 侧以
**「1 个模块 × 1 个用例」**的抽样，写下结论 **「AI 层是合规的」**；
执行方扩样至 4 模块 × 3 用例后，**抓到该模块之外的真违规**，推翻了该结论。

**而讽刺的是，写下该结论的同一份文档里，刚刚立下本条原则。**

**要求**：

```
结论的适用范围 ≡ 证据的适用范围
  实测 1 个模块 1 个用例 → 只能说「该模块在该用例上通过」
  未验的部分         → 必须写明「未验」，不得默认其合规
```

**推广**：凡写"X 是合规的 / 对的 / 没问题的"这类**全称判断**，
先自查一句 **「我验的样本，够不够支撑这个全称？」**

## 8.5 ★ 多入口一致性：必须用断言保证，不能靠人想起

> **当一段核心逻辑有 N 个调用入口时，改完核心不等于改完产品。**
> **"某个入口忘了接"必须由断言发现，不能靠人想起来。**

**已发生的实例**（事故 27）：真太阳时修复改了 `paipan()` /
`solarTime.ts` 核心，但**三个入口**中：
- 批命 `/api/paipan` ✅ 接了
- 紫微 `/api/ziwei` ✅ 接了
- **合婚 `/api/hemun` ❌ 漏了**（后来执行方自查补上）
- **地理 `/api/geo` ❌ 又漏了**（复核时才发现）

**危害不是"必然错"，而是"约一半情况下错"**：
偏移 56 分时，出生时刻落在每个时辰的前 56 分钟内 → 跨过边界 → 时柱改变
（≈ 47% 的出生时刻）；偏移超过一个完整时辰（如乌鲁木齐 −130 分）→ **必然改变时柱**。

**要求**：

```
① 改核心逻辑时，先列出【全部调用入口】（grep 调用点，不靠记忆）
② 新增一条【入口一致性断言】：
     同一份输入，遍历所有入口，输出必须一致
③ 该断言纳入 verify
```

**为什么必须自动化**：
这类遗漏**在单入口测试里完全看不出来**——每个入口单独测都是"通过"的，
只有横向比对才暴露。**而"人想起来有哪几个入口"这件事，重复失败率极高。**

**推广**：凡"一份数据/逻辑被多处消费"的场景（多个 API、多个页面、SSR 与 CSR 两路、
导出与展示两路），都属于本条管辖。

**正面解法参考**：把判据/逻辑收为**单一事实源**（shared module），
让所有入口**只能从同一处取**，从结构上消除分叉可能。

### 8.5.1 ★ 「单一事实源」只保证判据一致，**不保证每个消费者都接线了**

> **共享的判据存在 ≠ 共享的保护生效。**
> **判据收为单一事实源之后，必须另查一遍：应当消费它的地方，是不是都调用了。**

**已发生的实例**（事故 30）：`ai-check.ts` 作为合规判据的**单一事实源**建立成功，
`aiHemun` 把 `findForbidden`（禁用词）接进了重试校验，
**`aiAnalysis` 只接了 `unknownGanzhi`（干支溯源）** ——

| | 共享判据 | validate 接线 |
|---|---|---|
| `aiHemun` | `ai-check.ts` | `findForbidden` ＋ `unknownGanzhi` ✓ |
| `aiAnalysis` | **同一个** `ai-check.ts` | **只有 `unknownGanzhi`** ✗ |

**后果**：「务必／势必／必定」这类绝对化断言会从 `aiAnalysis` **直接上线**
（sanitize 只覆盖「不必」；「未必／不可避免」被否定式豁免正确放行，不是问题）。

**要求**：

```
建立/扩充共享判据时，除了"消费者都从同一处取"，
还要断言【每个消费者的 validate 都真的调用了它】。
—— 前者防"判据漂移"，后者防"接线遗漏"，是两件事。
```

**推广**：这与 §8.5 是同一族问题的两种方向 ——

| 规则 | 防的是 |
|---|---|
| §8.5 | **核心逻辑**改了，某个**入口**没接 |
| §8.5.1 | **共享判据**建了，某个**消费者**没调 |

**两者都必须由断言发现，不能靠人想起。**

## 8.6 ★ 断言必须「有牙」：用例须落在**判别边界内**

> **一条永远绿的断言，比没有断言更糟** —— 它给人虚假的安全感。
> **"断言跑通"不等于"断言能发现问题"。**

**判据**：

```
写完断言后必须自问：
  「我故意把这段逻辑改错，这条断言会不会红？」
  ——若不会红，说明用例没落在判别边界内，等于没测。
```

**已发生的实例**（事故 28）：入口一致性断言的**三个北美案例全部无牙** ——
真太阳时偏移 56 分钟，而案例时刻选在时辰的**中段**，
**校正前后落在同一时辰 → 时柱相同 → 漏接时区也测不出来**。
只有乌鲁木齐（偏移 −130 分 > 一个时辰）与北京保住牙口。

**如何找判别边界（以"偏移 Δ 分钟的修正"为例）**：

```
时辰 120 分钟一轮 → 出生时刻 T 只有在
      T 相对时辰起点 < |Δ|
时才敏感。选在边界外的时刻，断言恒绿。
（纽约 Δ=−56 → 只有每个时辰的前 56 分钟内出生才有牙）
```

**要求**：

1. **用例时刻/参数是刻意选的**，且**不能只靠注释说明** —— 见 §8.6.1
2. **头号场景必须自己有牙** —— 不能靠"其他案例有牙"来兜底
   （北美是本轮修复的目的，而北美案例恰恰无牙）
3. 若确实找不到有牙的用例，**说明该断言验不出这个改动**，应重新设计

### 8.6.1 ★ 把「刻意选择」变成断言，而不只是注释

> **注释保护的是"读注释的人"，断言保护的是"这个值本身"。**
>
> **对"静默退化"这类失效，注释是不够的。**

**判定标准** —— 凡**同时满足**以下两条的参数，都必须有对应的**自检断言**：

```
① 取值是【刻意选的】（非随手填）
② 【取错时测试不会失败，只会变弱】   ← 关键
```

**第 ② 条是核心**：
> **危险的不是"填错会报错"的参数，而是"填错只是不再有效"的参数。**

**已发生的实例**（事故 28 的修复）：牙口案例的时刻若被"顺手改成整点"，
断言**不会失败，只会失去意义**（恒绿）。处置：

| 手段 | 效果 |
|---|---|
| 只写注释"时刻是刻意选的" | 后人**读到了才**不犯错 |
| **加自检断言**（无校正时柱 ≠ 校正后时柱） | 改错**立刻翻红**，不依赖人读 |

**并且：守护牙口的那条断言，自己也要有牙。**
（实例中已验证：把时刻改回整点，该自检确实翻红 —— **递归应用本条**。）

### 8.6.2 ★ 涉及历史事实的期望值，必须有来源，不得从「现状」推断

> **测试里的"期望值"也是一个断言 —— 它同样不得编造**（红线 1 的延伸）。
> **尤其涉及历史事实时，必须查史料，不能从当下的状态反推。**

**已发生的实例**（事故 29）：DeepSeek 侧写逆命题用例时，把
**「昆士兰现在没有夏令时」当成了「昆士兰从来没有夏令时」**，于是
给 `Australia/Brisbane 1990-01` 填了期望 `0 分`，实测得 `−60 分` → 误报为"缺陷"。

**查史后**：昆士兰 **1989-10 至 1992-03 实行过夏令时**，
故 1990/1991/1992 年 1 月均为 UTC+11（应剥），1988 与 1993 之后为 UTC+10（不应剥）。
**实现完全正确，是期望值错了。**

**要求**：

```
凡期望值涉及以下之一，必须先取得来源再填：
  · 历史制度（夏令时起止、时区变更、行政区划调整）
  · 历史数据（某年的统计值、某版本的规则）
  · 已废止/已变更的规范
来源不明时，写「待查」并标红，不得凭印象填一个数。
```

**推广**：这条与 §8.4.6.1 是同一族错误的两个面 ——

| 规则 | 管的是 |
|---|---|
| §8.4.6.1 | **结论**的范围不得超出**证据**的范围 |
| §8.6.2 | **期望值**必须有**来源**，不得凭现状推断 |

**两者都在防同一件事：用手边的印象，代替手边没有的事实。**

### 8.6.3 ★ 查「某物已消失」时，判据必须匹配【旧形态】，而非【新形态】

> **断言"X 已经没有了"的时候，要拿 X【原来的样子】去搜，
> 不能拿 X【改后的样子】去搜。**
> **否则判据必然通过 —— 因为它搜的是一个本来就不该出现的东西。**

**已发生的实例**（事故 31）：变现管道 Part A 的验收 #2 是
「页面不得有硬编码价格」。我方写的判据是：

```
grep '29.99' / '19.99' 在 src/app/** 应为 0 命中
        ↑ 这是【新价】（$29.99）的数字
```

**而实际残留在页面里的是【旧价】** `¥19.9` / `¥29.9`
（`chart/page.tsx`、`mingshu/MingShuContent.tsx` 共 6 处）。

**→ 照跑这条 grep 会通过，缺陷却真实存在**（且用户可见：`/pricing` 显示 `$29.99`，
`/mingshu` 显示 `¥19.9`，两套价格两种币种）。

**要求**：

```
写"某物已消失/已清理/已统一"的断言时：
  ✗ 不要用【新值】去搜（新值本就不该出现在旧位置，搜不到是必然）
  ✓ 要用【旧值】、【旧格式】、【旧符号】去搜
  ✓ 更稳的做法：搜【类别标志】而非具体值
      —— 例如查人民币残留，搜符号 `¥\s*\d` 比搜具体数字可靠得多
      （符号不会随改价而变，数字会）
```

**推广**：这与 §8.6 同族，但方向相反 ——

| 规则 | 判据要落在 |
|---|---|
| §8.6 | **判别边界内**（能区分对与错的位置） |
| §8.6.3 | **缺陷的旧形态上**（要消失的东西本来的样子） |

**共同点**：**判据的形态必须与它要捕捉的对象的形态一致。形态错位 = 无牙。**

### 8.6.4 ★ 边界要穷举「结构自身的换位点」，不能只测「外部扰动造成的边界」

> **一个有多级结构的东西，每一级都有自己的换位点。**
> **把这些换位点【穷举】，与"测外部扰动造成的边界"，是两件事。**
> **只做后者，会留下整类盲区。**

**已发生的实例**（事故 32）：`paipan` 在 **23:00–24:00 的四柱自相矛盾** ——
**日柱按民用日 00:00 换日，时柱却按晚子时 23:00 推时干**，
于是 23:30 输出「日庚辰 ＋ 时戊子」，而五鼠遁规定庚日子时必是丙子。
**违反五鼠遁 10/10 处全部落在 23 点，其余 230 个时刻全自洽。**

**为什么长期没被发现** —— 我们此前在边界上做的工作**全部是"外部扰动"**：

```
真太阳时校正（−56 分）→ 出生时刻跨时辰   已测 ✓
夏令时剥离                             已测 ✓
```

**但从没测过「时辰自身的换柱点」** —— 即 **23:00 这个子时边界**。

**要求**：

```
给一个多级结构写边界测试时，先【列出每一级各自的换位点】，逐个覆盖：

  年柱 ← 立春（节气）
  月柱 ← 十二节（节气）
  日柱 ← 【子时】（23:00 或 00:00，流派相关）   ← 本项目漏掉的就是这个
  时柱 ← 每个整时辰（2 小时）

—— 然后用【不依赖流派的硬规矩】去验自洽性：
     年→月：五虎遁（年干推月干）
     日→时：五鼠遁（日干推时干）
   这类判据同时守住多种流派，只抓「内部矛盾」这一件事。
```

**推广**：这与 §8.6 是同一族，但管的是**覆盖**而非**形态** ——

| 规则 | 管的是 |
|---|---|
| §8.6 | 判据**有没有牙** |
| §8.6.3 | 判据**形态对不对** |
| §8.6.4 | 判据**盖没盖全**（该测的换位点测了没有） |

**三者合起来才是完整的"断言质量"：有牙 · 对形态 · 全覆盖。**

### 8.6.5 ★ 比对两个对象时，判据必须覆盖其【全部实质内容】，不能只比外壳

> **比"两个东西是否相同"时，判据取到什么字段，就只保证了那些字段。**
> **取到的是骨架，得出"相同"就毫无意义 —— 那是假绿。**

**已发生的实例**（事故 33）：DeepSeek 侧核查「紫微在 23:30 是否算错日」时，
写了比对函数：

```js
const fp = (ch) => ch.palaces.map(p => `${p.name}:${p.ganZhi}`).join('|')
                                              ↑ 只取了宫位干支
// 另有一处取 p.stars —— 该字段不存在，取到 undefined（静默为空）
→ 结论："命宫/星曜全盘比对 ✓ 完全相同"        ★ 假绿
```

**改用 `majorStars / minorStars / adjectiveStars` 完整比对后，真相是**：

```
2026-01-06 23:30  命宫 武曲,天府   官禄 紫微,天相
2026-01-07 00:30  命宫 紫微        官禄 廉贞,天府
                  → 12 个宫位的主星【全部不同】，差异率 92.3%
```

**命宫干支相同（骨架没变），但里面每一颗星都换了 —— 用户最难察觉的那类错。**

**要求**：

```
写"两者是否相同"的判据时：
  ✓ 先列出被比对象的【全部实质字段】，逐类覆盖
  ✓ 取不到的字段会【静默为空】而不是报错 —— 必须显式断言"字段确实取到了"
  ✓ 骨架（结构/ID/名称）相同 ≠ 内容相同；内容字段必须单独比
  ✗ 不要把"没取到的字段"当成"比过了"
```

**与 §8.6 家族的关系**：

| 规则 | 管的是 |
|---|---|
| §8.6 | 判据**有没有牙** |
| §8.6.3 | 判据**形态对不对** |
| §8.6.4 | 判据**盖没盖全**（边界） |
| **§8.6.5** | **判据盖没盖全（内容字段）** |

### 8.6.6 ★ 规格里凡有「数字 ＋ 语义」两部分，断言不能只盖数字

> **数字最容易断言，所以最容易被断言；而语义才是产品真正卖什么。**
> **只断言数字 = 只证明了价格对，没证明卖的东西对。**

**已发生的实例**（事故 35）：变现管道 Part A 的价目表有 9 个 SKU。
我方断言了**全部 9 个价格**（`test-pricing-accept.mjs`，且纳入 verify），
**却一个「权益」都没断言** —— 而实现把会员权益写成了「深度报告不限次数」：

```
命书单次 $29.99      vs      月度会员 $9.90（深度报告不限次数）
→ 买 1 份都不如开会员 → 价格表上 6 个报告 SKU 全部作废
→ 客单价被压到 $49/年封顶，付费墙在结构上无法成立
```

**根因**：`Sku` 里只有 `priceUSD` 是结构化的，**权益只存在于中文 `desc` 里**；
而任务书里写过的 `grants: GrantRule[]` 被略过，验收也没盖。
**→ 价格一分不差、权益完全跑偏，`verify` 全绿。**

**要求**：

```
规格里每一处「数字 ＋ 语义」并存的地方，断言必须【两条都盖】：
  数字：价格 / 额度 / 天数 / 上限      ← 容易，通常已盖
  语义：买到什么 / 解锁什么 / 限制什么  ← 容易漏，且往往才是产品本身

—— 且"语义"必须【数据化】才可能被断言（写进中文描述里的语义，断言抓不到）。
```

**与 §8.6.5 的关系**：§8.6.5 说「比对要覆盖全部实质内容」；
本条说「**规格的断言也要覆盖全部字段，而不只是最容易量化的那个**」。
两者同一族：**别让"容易测的那部分"冒充"全部"。**

### 8.6.7 ★ 验证手段本身必须先被验证（§8.6.1 的推广）

> **断言保护值；那么谁来保护断言？**
> **§8.6.1 说「守护牙口的断言，自己也要有牙」。本条把这句话推广到【验证手段】的全部形态。**

**形态一：变异注入必须真的改变行为**

**已发生的实例**（事故 36）：DeepSeek 侧复核「统一晚子时」时，为验证守护断言有牙，
把 `analyzeZiwei` 的 `chart.ziweiDateStr` 改回从 `chart.input` 推导 —— **退出码 0，没红**。
追查发现：**该案例中校正前后的「日期」恰好相同**（只有时辰从寅变丑），
**改的是一个等值字段 → 那次注入根本没有产生变异** ✓ 断言正确地保持绿色。

```
★ 变异测试前，先确认这次变异【真的改变了行为】：
   · 记录变异前后的被测输出，二者必须不同
   · 若相同 → 这次注入不构成证据（而不是「断言无牙」）
   · 另一坑：注入文本在 shell/转义层被吃掉，报出的是【语法错误】而非断言失败
     —— 退出码非 0 不等于「断言红了」，必须看【失败原因】

★★ 而且：【确认注入有效】这一步失败 ⇒ 【立即中止】，不得继续跑断言测试。
   因为注入无效时，测试的红是【不知情】的 —— 分不清是断言命中还是编译/转义失败。
   纪律顺序必须是：① 注入 → ② 确认输出真的变了（且语法有效）→ ③ 才跑断言。
   ②不通过就停，任何来自③的红都不作数。

★★ 且「确认」必须是【肯定性证据】—— 打出改变后的实际值并与预期比对。
   不得以「退出码 0」或「无输出」代替确认：那只是【没有坏消息】，不是确认。
   闸门写成 `if (退出码 ≠ 0) 中止` 时，一个什么都没做的空脚本也会通过 ✗
   最好把确认【本身写成一条断言】（如 `计数 == 7` 不成立即中止）。
```

**★ DeepSeek 侧在此事上连错四次（都记在自己账上，被注入的代码每次都是对的）**：

```
① 改了个【等值字段】—— 该案例校正前后「日期」恰好相同，注入没产生变异（verify 正确地保持绿）
② 注入文本里的 ${} 被 shell 吃掉 —— 报的是 esbuild Transform failed（语法错误）
③ 插入裸标识符当注入标记 —— 又报 Expected "}" but found "甲子"（语法错误）
   ★ 且第 ③ 次在【第 1 步已失败】的情况下仍跑了断言测试 —— 那次红色完全不可采信
④ 确认步骤【打印为空】，而闸门只看「退出码 ≠ 0」→ 空输出通过了闸门
   ★ 那次演示之所以仍成立，是靠第 2 步的断言输出自证，不是靠闸门
```

**形态二：测试辅助函数不得替被测代码做容错**

**同一实例的另一半**：`test-dayboundary-accept.mjs` 的辅助函数 `atLocal` 里有

```js
let hh = g('hour'); if (hh === 24) hh = 0      // 辅助函数归一化了 '24'
```

**而生产函数 `dailyDateInZone` 没有归一化** —— 于是：

```
运行环境若返回 '24'（hour12:false 在部分 ICU 实现下把午夜给成 24）：
   · 测试：辅助函数归一化 → 找到正确时刻 → 断言全部通过
   · 生产：hour >= 23 成立 → 【午夜被推进一天】
→ 测试替生产挡掉了缺陷
```

**而且用例用的是 23:30 与 00:30，两头都避开整点，而 `'24'` 只在恰好午夜出现** ——
**辅助函数挡一层、用例不覆盖再挡一层，构成双重盲区。**

```
★ 测试辅助函数只做「定位/构造」，【不得做被测代码本应做的容错】；
  否则测试的善意会掩盖生产的缺陷。
★ 边界用例要覆盖【边界值本身】（00:00 整点），而不只是「边界附近」（23:30 / 00:30）。
```

**三合一**：§8.6.1（守护断言的断言）· §8.6.7-一（注入要真变异）· §8.6.7-二（辅助不替生产容错）
—— **同一个原则：验证手段自身也必须被验证。**

### 8.6.8 ★ 计数阈值只是「属性」的影子 —— 断言要盖属性本身，不能只盖当年那个数

> **「计数」是最容易写出来的断言形态，所以最容易被写出来；
> 但它往往只是你想防的那个「属性」的一个投影。**
> **投影达标 ≠ 属性达标。**

**已发生的实例**（事故 38）：通用日签返修时，发现变体 2 有 **57/60 以「心」字起句**（句式定式）。
返修后立了断言：

```
变体[2]「心」开头 ≤ 15/60      实际 15  ✓ 绿
变体[1]「事情」开头 ≤ 5/60     实际 4   ✓ 绿
变体[1]「到了」       ≤ 5/60   实际 3   ✓ 绿
```

**但若日后有人把其中 3 条都改成以「心在」开头**：

```
计数仍是 15  → 断言【依然绿】
而定式已经回来了 ✗  ← 你想防的事情发生了，断言毫无反应
```

**根因**：真正要防的属性是「**句式定式**」，而「心开头 15 条」只是它的**一个影子**。

```
★ 写断言时先问一句：
    「这个断言在什么情况下会绿，而我想防的事情已经发生了？」
  若答得出来 → 这个断言盖的是影子，不是属性。
★ 补法：为属性【本身】写断言。
   本例：逐变体「单一前两字最高频次 ≤ 6/60」
        —— 直接量定式，且能覆盖未来任何新出现的定式（不只是「心」「事情」「到了」）
★ 影子断言可以保留（它盯防已知重点），但必须有属性级断言兜底。
```
★ 操作化推论：【计数非零 ≠ 内容存在】。拿到 1 个结果，必须【打印它是什么】再下结论。

**与 §8.6.6 的关系**：§8.6.6 说「数字＋语义两部分，断言不能只盖数字」；
本条说「**数字达标不等于语义达标 ——尤其当数字只是语义的影子时**」。
**两者同族：别让「容易测的那部分」冒充「真正要守的那部分」。**

**验证三件套**：`npx tsc --noEmit` + API 事实核对 + 浏览器实测
