# 日运 / 日签 —— 设计说明（含订阅权益）

> **性质**：设计稿 ＋ 待拍板项（§六）＋ 可转 TraeCode 的落点（§三、§四）
> **日期**：2026-10-07
> **缘起**：定价方案指出订阅缺「高频钩子」；用户决定增加日运/日签

---

# 〇、为什么做这个（先明确价值）

上一轮对比 FateTell 时暴露的缺口：

```
FateTell 的订阅（$59.99/年）卖的是【高频】：
  大司命对话 20次/日、AI占卦 5次/日、日签解锁
而我们所有功能都是【一次性深度内容】→ 订阅没有存在理由
```

**日运/日签正是补这个缺口的标准解法** —— 它把"一次性算命"变成"每天来一次"。

**但它是这个产品里风险最高的功能**，所以本设计有一半篇幅在讲**边界**。

---

# 一、★ 定位：做「今日一省」，不做「今日吉凶」

## 1.1 一个必须先承认的技术事实

命理的影响力层级是：**大运 > 流年 > 流月 > 流日**。

**流日是噪声最大的层级。** 而我们已立的规矩（总纲 §8.3）已经说过：

> 流月只用「较宜／一般／宜慎」—— **因为月度吉凶本就无凭**。

**日运的颗粒度比流月更细 → 更无凭。**

**如果流月不能说「大吉」，日运就更不能说「今日大凶」。**

## 1.2 所以定位是「自省引子」，不是「预测判决」

| | ❌ 不做（今日吉凶） | ✅ 要做（今日一省） |
|---|---|---|
| 形态 | "今日大凶，忌出行签约" | "今日**壬子**，与你的日柱同气，**宜静**；**留意**情绪起伏" |
| 依据 | 只给结论 | **点明干支与关系** |
| 语气 | 判决 | 提醒 |
| 用户动作 | 改行程（被支配） | 自省（自主） |

**一句话**：

> **我们不卖"今天能不能做某事"，我们卖"今天值得留意什么"。**

**这不是退让，是差异化** —— FateTell 的日签是"运势"，我们可以是"每日一省"，
而这更贴合产品调性（用户自己就读佛经、道德经）。

## 1.3 ★ 为什么这条定位关系到生死

日运是**最容易变成"迷信放大器"**的功能：

- 用户每天来看 → 逐渐用它指导日常决策
- 而它恰恰是**最无凭的一层**
- **测测被 3·15 点名批评的「隐秘的成瘾机制」**，日运正是这类机制的载体

**我们前面刚定的红线**（不做恐吓式、不给绝对断言、低客单）——
**日运是这套红线的最大压力测试点。**

# 二、产品形态：两层

**用户的诉求是"订阅用户有日运/日签"。我建议拆成两层** —— 理由见 2.3。

## 2.1 免费层：**通用日签**（获客 / 分享）

```
┌──────────────────────────────┐
│      2026年10月7日 · 壬子日        │
│                                  │
│   「水性至柔，而能穿石。           │
│     今日宜缓不宜急。」             │
│                                  │
│   壬子 · 六十甲子第 49 位          │
│   ───────────────  fate.example   │
└──────────────────────────────┘
```

- **内容**：当日干支 ＋ 一句**意象/自省**（不看个人盘）
- **可导出图片分享**（带产品标识）→ **获客**
- **文案资产**：60 甲子 × 3 变体 = **180 条**（180 天不重复）

## 2.2 订阅层：**个性化日运**（留存）

在通用日签之上，**结合用户命盘**：

| 区块 | 内容 | 数据来源 |
|---|---|---|
| 今日干支 | 壬子 | 新增 `liuRi` 计算 |
| **今日十神** | 日干壬对日主 X 为「比肩」 | 已有 `SHI_SHEN` 表 |
| **与原局的关系** | 今日日支子 **与你的日支 X 半合／相冲** | 已有 `LUCK_CHONG` / 合局表 |
| **叠加大运流年** | 今日落在大运 Y、流年 Z 之下 | 已有 `luckCycles` |
| **与流月的呼应** | 本月（丙午月）节律中，今日处于… | 已有 `buildLuckLiuYue` |
| **一句宜慎** | "宜静、宜整理；注意情绪" | 静态文案资产（见 §3.3） |

## 2.3 为什么建议拆两层（而非只给订阅）

| 理由 | 说明 |
|---|---|
| **传播价值 > 付费价值** | 日签天生适合分享（图片、短句）。**免费才能发挥它的获客作用**；锁在订阅里等于放弃拉新 |
| **订阅需要"更个人化"** | 通用日签**不足以让人付费** —— 它和天气 App 一样，谁都能做。**"结合你的盘"才是订阅理由** |
| **降低合规压力** | 免费层是通用内容（不涉个人吉凶断言），**风险最低**；个性化判断只在订阅层出现，可控 |

> 若你坚持"日签也只给订阅"，也可行 —— 但会同时损失**获客**与**订阅说服力**两点。

# 三、技术设计

## 3.1 流日计算：**比流月简单得多**

**关键差异**：

| | 边界 | 说明 |
|---|---|---|
| 流年 / 流月 | **节气** | 已有 `JIE_BY_MONTH` 处理 ✓ |
| **流日** | **不需要节气** | **日柱是连续的 60 甲子循环** |

**所以流日 = 取指定日期的日干支**，用现有的 `lunar-javascript` 可直接得到：

```ts
// 伪代码
const lunar = Lunar.fromDate(someDate)
const dayGanZhi = lunar.getDayInGanZhi()   // 或等价 API
```

**新增**：`LuckLiuRiItem` 与 `buildLiuRi(date)` —— 应当**复用** `analysis.ts` 里既有的
十神表、干支关系表（`LUCK_CHONG`、合局表），**不要另造一套**（总纲 §8.5.1）。

## 3.2 ★「今天」怎么定：这是本功能第一个真问题

**三个候选**：

| 方案 | 问题 |
|---|---|
| 服务器日期 | ❌ 用户在美国、服务器在 UTC → 会错一天 |
| **用户当前时区** | ✅ **推荐** —— 复用已有的 `currentCity` / `birthZone` 基础设施 |
| 出生地时区 | ❌ 生在纽约、现住上海的人，"今天"应按上海 |

**另一个子问题：日与日的分界**

| 命理惯例 | 产品现实 |
|---|---|
| **子时换日（23:00）** | 用户 23:30 打开，会看到"明天"的运势 → **困惑** |
| **民用日（00:00）** | 符合直觉 ✓ |

**我建议：日运按【民用日 00:00 + 用户当前时区】** ——
并在 UI 注明"命理排盘用子时换日，此处按自然日"。

**这属于「刻意选择」，须显式说明**（总纲 §8.4.4）—— 否则下一轮会被当成 bug 提回。

## 3.3 ★★ 文案必须是【静态资产】，不能按用户实时调 AI

**这是本设计最关键的技术约束，有两条理由。**

### 理由一：成本会随用户数线性放大

```
假设 10 万订阅用户，每人每天看一次日运：
  实时 AI：10万 × $0.0005 ≈ $50/天 ≈ $1500/月  ← 而且延迟明显（用户打开要等）
  静态文案：$0                                 ← 且零延迟
```

**一次性深度报告可以接受 AI 延迟（用户愿意等 30 秒），
但"每天打开看一眼"绝不能等。**

### 理由二（更重要）：**静态文案可以逐条审核**

> 我们要保证"不给绝对断言、不恐吓"。
> **实时 AI 生成的内容无法逐条审核；而 180/300 条静态文案可以逐条过目。**

**这对一个把"不给错误信息"当红线的产品，是决定性的。**

### 组合数估算（可控）

```
个性化日运的文案维度：
  今日日干对日主的十神        : 10 种
  今日日支与原局的关系（归并） :  约 6 类（同气／六合／六冲／相生／相克／无关系）
  ─────────────────────────────
  组合                        : 约 60 种 × 每种 3–5 变体 = 180–300 条
```

**这 180–300 条 = 一个可审核、可迭代的内容资产**（AI 批量生成 ＋ 人工过目 ＋ 逐条合规检查）。

**通用日签**：60 甲子 × 3 变体 = **180 条**。

## 3.4 缓存与渲染

| 项 | 策略 |
|---|---|
| 流日干支 | 全局（同一时区同日同值）→ 可进程内缓存 |
| 通用日签（180 条） | **构建期内联进代码**，运行时零 IO |
| 个性化日运文案（~300 条） | 同上；按 `(十神, 关系)` 查表 |
| 日运接口 | 按 `(chartId, 民用日, tz)` 缓存；或实时查表（计算量极小） |
| **分享卡片图片** | 服务端生成或前端 canvas 导出；**带产品标识** |

# 四、订阅权益与门禁

## 4.1 权益表

| 能力 | 免费 | 订阅 |
|---|---|---|
| 今日干支 ＋ 通用日签 | ✅ | ✅ |
| 分享卡片 | ✅ | ✅ |
| **今日十神 / 与原局关系 / 叠加大运流年** | ❌ | ✅ |
| **今日宜慎（个性化）** | ❌ | ✅ |
| **与流月的呼应** | ❌ | ✅ |

## 4.2 ★ 门禁必须走 `entitlements`，不能在页面里判断

依定价方案 §4.2 的**单一判定函数**：

```ts
// 新 SKU 与权益
type SkuId = ... | 'member_monthly' | 'member_yearly'
// 日运属【会员权益】，不是单次 SKU
canViewDaily(ent) = ent.member
```

**⚠️ 并且注意定价方案 §4.2③ 那个洞**：
**`/api/daily` 也必须在服务端判定** —— 未授权时**不返回个性化字段**，
不能"前端隐藏、后端照发"。

# 五、合规红线（六条，必须写进实现）

| # | 红线 |
|---|---|
| 1 | **禁用「大吉／大凶／必定／务必」** —— 与既有 AI 层判据一致（`ai-check.ts`） |
| 2 | **禁用「今日必……」绝对断言** |
| 3 | **禁恐吓式** —— 不做"今日大凶、忌出行"；不做"不化解会有灾" |
| 4 | **必须点明依据** —— "今日壬子、与日柱同气"，而不是光给结论 |
| 5 | **不做成瘾式推送** —— 不做"你已 N 天没查、运势下滑"这类召回 |
| 6 | **日运同样需要免责声明** —— 且**措辞要弱于**报告（粒度更细、更无凭） |

**并建议**：把日运文案**纳入既有的合规检查脚本**
（`test-checker-accept.mjs` 同族的离线断言）——
**300 条文案可一次性扫禁用词，这是静态资产的又一个好处。**

# 七、落地顺序

```
第 1 步   流日计算（buildLiuRi）＋ 复用既有十神/关系表
             ↓
第 2 步   通用日签：60 甲子 × 3 变体 = 180 条静态文案
          （可先做这一层，独立上线，用于获客）
             ↓
第 3 步   个性化日运：~300 条静态文案（十神 × 关系组合）
             ↓
第 4 步   /api/daily：服务端按 entitlements 分层返回
             ↓
第 5 步   分享卡片（导出图片 + 产品标识）
             ↓
第 6 步   文案纳入合规检查脚本（离线扫禁用词）
```

**第 1–2 步可独立上线**（免费通用日签），**不依赖支付接入**。

# 八、一句话

> **日运是补订阅空缺的正确选择 —— 但它是这个产品里风险最高的功能。**
>
> **因为它在命理影响力层级里最弱（大运 > 流年 > 流月 > 流日），
> 却在用户的日常决策里最贴身。** 粒度最细、最无凭、最容易被当成指导。
>
> **所以定位要是「今日一省」，不是「今日吉凶」** ——
> 不给"能不能做某事"的判决，只给"值得留意什么"的提醒。
>
> **而技术上有一条硬约束：文案必须是静态资产，不能按用户实时调 AI。**
> 一是成本随用户数线性放大、延迟不可接受；
> **二是——更要紧的——静态文案可以逐条审核，而实时生成的内容不能。**
> 对把"不给错误信息"当红线的产品，这一条是决定性的。
>
> **最后**：日签建议**免费**（它的传播价值远大于付费价值），
> **个性化日运才是订阅权益** —— 通用日签不足以让人付费，但足以让人认识你。
