# 查询页矩阵方案：nongli.info 拆解与 mingcharts 落地路径（2026-11-12）

> 本文分两段：前半是调研与方案（2026-11-12 上午），后半是执行裁决与 GSC 基线（同日核对后追加）。
> 所有数字都标注来源与口径；公开数据取不到的地方写「未找到可靠来源」，不填推测值。

---

## 0. 结论摘要

1. **nongli.info 是日历工具站，不是内容站。** 它的骨架是「日期页 + 月页 + 年表页 + 转换工具」，全站可抓取 URL 的绝对主体是日期页（推算约 7.3 万条），静态文章只有 60 条左右。此前一份调研把它描述成「生肖年龄长尾内容页」是错的，需要纠正。
2. **但它的自然搜索入口确实集中在年龄/年次这一类查询。** Semrush 公开页（台湾库，2026-08）给 nongli.info 列出的前 5 个自然关键词全部是「屬 X 今年幾歲」，单条月搜索量 6,600–9,900。这说明「站点类型」和「关键词入口」是两件事，不能用一个标签概括。
3. **它的流量主体不是搜索，是习惯性直接访问。** 2026-08 全站 168.98K 访问，其中自然搜索 27.78K（16.4%），桌面端来源里 Direct 占 62.01%、google.com 占 29.52%。所以「靠几万条长尾日期页吃搜索流量」这个假设，公开数据不支持。
4. **mingcharts 缺的不是日期页数量，是三类查询入口：岁数型、民國年次型、農民曆日期型。** 干支型没有找到独立搜索需求证据，宜忌型应作为日期页的模块而不是独立页。
5. **建议第一批只铺 64 页**（12 个生肖年龄页 + 51 个民國年次页 + 1 个年次 hub），全部繁体、全部有公开关键词量支撑。第二批再铺農民曆年/月/日页，日页采用「窄窗口索引 + 不进 sitemap」的策略，避免重演 /bazi 日页的老问题。
6. **与现有 noindex 策略没有直接冲突**：新页面走新路由（`/tw/nongli/*`、`/tw/age/*`），不复用 `/bazi/{y}/{m}/{d}`。真正需要裁决的是「新日期页要不要进 sitemap」，本文给的是先不进。

## 2. nongli.info 页面结构拆解

### 2.1 站点类型判定

**是日历/转换工具站。** 三条硬证据：

1. 首页主体就是一张月历表，每格是「公历日 + 农历日」，点击进入日页（S1）。
2. robots.txt 允许抓取的目录是 `/duizhaobiao/`、`/days/`、`/years/`、`/shengxiao/`、`/huangli/`、`/birthday/`、`/zangli/`（S2）——全部是日历/换算/工具目录。
3. 站点自述：「本站提供西元 1901 年至 2100 年间的万年历、农历生日查询、农历转国历、国历转农历服务以及农历国历对照表」（S1）。

首页导航可直接数出 **60 余个静态入口**（14 个节日、24 个节气中的 7 个带链接、13 个拜拜日期、7 个知识页、15 个月份对照表入口、3 个年页、生肖 4 个、择日 2 个等）。这些是站点的「薄内容外壳」，真正的体量在日期页。

### 2.2 页面类型、数量与可抓取性

年份跨度 1901–2100，共 200 年（S1）。

| # | 页面类型 | URL 形态 | 推算页数 | robots 是否允许 | 说明 |
|---|---|---|---:|---|---|
| 1 | 万年历日页 | `/index.php?year=&month=&date=` | ~73,050 | **否** | `Disallow: /*?*` 命中；不在 Allow 目录内 |
| 2 | 万年历月页 | `/index.php?year=&month=` | ~2,400 | **否** | 同上 |
| 3 | 黄历日页 | `/huangli/days/index.php?year=&month=&date=` | ~73,050 | **是** | `/huangli/` Allow 规则比 `/*?*` 更长，按最长匹配生效 |

**关键结论（B 级推算，但公式明确）**：nongli.info 实际被 Google 允许抓取的日期页只有 `/huangli/days/` 这一套，约 **7.3 万条**；根目录那套万年历日页被 `Disallow: /*?*` 挡在索引之外。也就是说，它不是「7 万条页面全部参与排名」，而是「一套日期页 + 一套被挡住的日期页」。

> 这条对 mingcharts 直接有用：**日期页不是越多越好，先决定哪一套进索引，再决定铺多少条。**

另有两条技术事实：

- `/sitemap.xml` 抓取返回空，**未发现 XML sitemap**。
- `Bingbot`、`MSNbot` 被整站 `Disallow: /`，即放弃必应流量（S2）。

### 2.3 单页信息结构（以 2026-11-12 黄历日页为例，S4）

实测页面从上到下的模块顺序：

1. **H1**：`2026年11月12日農民曆/黃曆`
2. **整月日历网格**（7 列，周日起）：每格 = 公历日 + 农历日 + 当日干支（如「十月初四 / 己亥 庚寅」）；节气日显示节气名替代农历日
3. **三向翻页**：`<<上一个月` / `當前月` / `下一个月>>`，参数里保留 `date=12`，翻月不丢「日」
4. **查询表单**：年（1901–2100 下拉）、月（1–12）、日（1–31），GET 提交回同一页
5. **当日黄历数据块**（核心）：
   - 西曆 / 星期 / 星座
   - 農曆（年月 + 大小月 + 日）
   - 歲次（年干支 + 月干支 + 日干支）
   - 四柱（年柱、月柱、日柱；注明时柱见下方时辰）
   - 胎神占方
   - 五行 + 執位（如「松柏木 平」）
   - 沖煞（沖猴(甲申)煞北）
   - 彭祖百忌（两句）
   - 吉神宜趨（8–10 个）
   - 凶神宜忌（4–5 个）
   - **宜**（7–13 项，逗号分隔）
   - **忌**（5–7 项）
   - 「農民曆宜忌名詞解釋」内链
6. **十二时辰格局**（12 条）：每条 = 时段 + 时干支 + 冲煞 + 神煞 + 宜 + 忌
7. 底部另有约 600 字的「農民曆的歷史演變」通识段（黄历入口页可见，日页正文以数据为主）

**正文长度**：日页以表格/列表为主，散文字数很少（数据项折合约 1,200–1,600 字的信息量，但不是连续正文）。它靠「数据完整」而不是「文章厚度」拿排名。

> **可借鉴**：模块顺序本身就是一条完整的查询动线——先回答「今天几号、农历几号」，再给干支，再给宜忌，最后给时辰。
> **不可借鉴**：全站复用的通识段。mingcharts 的日页必须至少有 2–3 句由当日数据推导出来的独有句子，否则 730 页会被判成套模板。

### 2.4 内链组织

| 机制 | 具体做法 | 对应 S |
|---|---|---|
| 月历网格 | 每个日格直接链到日页，日页顶部再放同一个网格（自指也在其中） | S1、S4 |
| 前后月 | 固定三个链接：上一个月 / 当前月 / 下一个月，保留 `date` 参数 | S1、S4 |
| 年表页 | 单页把 12 个月、约 365 行全部平铺，**无分页** | S5 |
| 对照表页 | 按月聚合，只有 12+8 个入口；页内逐日列出「农历 X 月 X 日 → 国历 Y 年 M 月 D 日」 | S6 |
| 择日页 | 年页 → 12 个月页；年页顶部直接给「2026 年宜结婚的吉日共 125 天」 | S7 |
| 生肖 | 年份表是 12 列 × 17 行的大表（1900–2103），年龄对照页按生肖下拉 | S8 |
| 全局导航 | 首页按「节日 / 生肖 / 拜拜 / 知识 / 对照表」分块，每块 3–15 条 | S1 |

**没有的东西**（这点很重要）：

- 没有 XML sitemap
- 没有分页（所有聚合页都是单页全量）
- 没有「年份索引页 → 月份索引页 → 日期页」三级树；年份本身就是 `/years/index.php?year=` 一张总表
- 没有面包屑式的结构化内链，靠月历格子承担主要权重传递

### 2.5 nongli.info 的可借鉴 / 不可借鉴

| 可借鉴 | 理由 |
|---|---|
| 日期页做成「数据块 + 时辰表」 | 用户要的是一次看全，不是读文章 |
| 月历网格做内链主干 | 365 条链接自然分布，不需要额外索引页 |
| 年表页单页全量 | 一个 URL 承接「2026 农历国历对照表」这类年查询，比 12 个月页更集中 |
| 择日页按「用途 × 年/月」切 | 结婚、搬家、开业是真实择日需求，且能自然导向工具 |

| 不可借鉴 | 理由 |
|---|---|
| 7.3 万条日期页全量生成 | 抓取预算会崩；本站已有 528 条「已发现 - 尚未编入索引」的教训 |
| 全站复用同一段通识正文 | 会被判薄内容，尤其在新站阶段 |
| 查询参数当 URL | 无法做 canonical/hreflang，也没法进 sitemap |
| 放弃 Bing | 本站的英文/海外用户里 Bing 仍有份额，不必学 |

### 3.2 渠道结构（S10）

- 自然搜索：**27.78K**（占 168.98K 的 **16.4%**），环比 −5.02%
- 付费搜索：**0**

**不进 sitemap**。只提交 hub、年、月三层。这与现有 `/bazi` 日页纪律一致（noindex 且不提交），区别是这里给了一个窄窗口开放索引。

**预渲染**：`generateStaticParams` 只预渲染「当月 + 次月」，其余 `dynamicParams = true` 按需 ISR（`revalidate = 86400`）。直接复用 `/bazi` 日页已经踩过的坑与结论（见 [test-day-page-crawl.mjs](file:///e:/ai-agent/MINGCHARTS/bazi-mvp/scripts/test-day-page-crawl.mjs)）。

### 5.6 第三批：F 择日聚合页（6 页，可选）

`/tw/nongli/ze-ri/{jiehun,banjia,kaishi,jiaoche,lifa,zhuangxiu}`，每个页面列出当年所有吉日（表），链到对应日页。6 页，索引、进 sitemap。

依据：`老黄历` 2,400、`黃曆` 1,900、`今日黄历` 720（S13，美国库），择日是黄历类最稳定的商业意图。但台湾库量级未取到，所以放 P2。

## 6. 与现有 noindex 策略的冲突与裁决

### 6.1 不冲突的部分（先说清楚）

- 新页面路由是 `/tw/nongli/*` 与 `/tw/age/*`，与 `/bazi/{y}/{m}/{d}` 完全不同路径，**不共享 noindex 规则**。
- 现有 `proxy.ts` 的 410 规则只匹配 `/bazi/*` 与 `/tw|en/bazi/*`，**不会误伤新路由**（[proxy.ts](file:///e:/ai-agent/MINGCHARTS/bazi-mvp/src/proxy.ts#L75-L125)）。
- 1950–1989 月页 noindex 的年份集合（1950–1989）与新农名历年份集合（2025–2027）**不重叠**。
- `/tw/bazi` 深链 410 不影响 `/tw/nongli`。

### 6.2 需要明确裁决的三件事

| # | 问题 | 裁决 | 理由 |
|---|---|---|---|
| 1 | 新日页要不要进 sitemap？ | **不进**，只提交 hub/年/月 | 站内已有 528 条「已发现 - 尚未编入索引」，其中 430 条是 `/bazi`。抓取预算是当前最大瓶颈，不能再灌 1,095 条 |
| 2 | 新日页要不要全量 index？ | **只放今天 −7 ～ +60 天的窄窗口**，其余 noindex,follow | 既保住「今日/近日」的真实搜索，又不制造一千余条零点击的索引页 |
| 3 | 要不要顺手把 `/bazi` 日页、1950–1989 月页放开？ | **不要** | GSC 实测：`/bazi` 全段 28 天 1,318 展示、0 点击；日页 2.2 万条薄内容。放开只会重演薄内容问题 |

### 6.3 与现有策略的「表面矛盾」

原方案曾打算让 P1 農民曆月页进 sitemap，而现有 sitemap 注释写的是「`/bazi` 月页暂缓提交」。两者的判据本来不同：

- `/bazi` 月页：252 个有展示、**0 点击**（2026-10-20 ～ 11-08，见 [SEO-改版基线](file:///e:/ai-agent/MINGCHARTS/bazi-mvp/docs/SEO-改版基线-2026-11-10.md)）——已证伪。
- 農民曆月页：36 页，背后是 `農民曆 2024` 9,900 的品类词，**尚未证伪**。

但本轮已裁决 P1 押后，**这个矛盾本轮不出现**。2026-11-12 又修正了一次：**P0 的 64 页进 sitemap**（原「一律不进」的靶子是日页薄内容，不适用于这 64 个有真实搜索需求的页），**将来的 1,095 条日页仍不进 sitemap**。等 P1 重启时再按上面两条判据单独裁决日页。

### 6.4 GSC 口径核实（2026-11-12，已定稿）

**核实时点**：2026-11-12，GSC 页面显示「上次更新日期：5.5 小时前」。

**口径**：

| 项 | 核实结果 |
|---|---|
| 属性 | **`sc-domain:mingcharts.com`**（网域资源，不是 URL 前缀资源） |
| 页面 | Search Console › 成效 › 搜索结果 |
| 时间范围 | **最近 28 天**，GSC 实际覆盖 **2026-10-20 ～ 2026-11-10** |
| 筛选条件 | **无**。搜索类型为默认「网页」，国家/地区、设备、页面均未加筛选 |
| 28 天总计 | **110 次点击 / 5,081 次展示**（CTR 2.16%） |
| 最近 7 天 | **53 次点击 / 1,564 次展示**（2026-11-04 ～ 11-10） |

**对两处旧数字的解释**：

1. 仓库文档写的属性是「`https://www.mingcharts.com`（含 www）」，**与实测不符**，应更正为 `sc-domain:mingcharts.com`。这是域名资源，天然包含 www 与非 www，不要再按 URL 前缀资源去理解。
2. 任务描述里的「每天约 55 次曝光、周点击 52」：
   - 「周点击 52」≈ 最近 7 天的 53 次点击，对得上；
   - 「每天 55 次曝光」是拿 **7 天展示 1,564 ÷ 28** 算出来的（≈55.9），属于把 7 天分子套了 28 天分母。真实日均是 **182 次/天**（28 天口径）或 **223 次/天**（7 天口径），不是 55。
3. 旧文档的「28 天 5,039 展示 / 88 点击」是 2026-11-10 的取数快照；GSC 会回填并修订历史数据，两天后同一属性同一窗口已变为 5,081 / 110。两者不矛盾，但不能逐日相减来做归因。

**铺页前基线（本轮唯一口径）**：

```
属性：sc-domain:mingcharts.com
窗口：最近 28 天（GSC 实际覆盖 2026-10-20 ～ 2026-11-10）
筛选：无
基线：110 点击 / 5,081 展示 / CTR 2.16%
```

**归因规则**：新页上线四周后，用「同一属性 + 最近 28 天 + 无筛选 + 当天重新导出」与上面这组数做对比；不要拿 11-10 的旧文件当分母，也不要把 7 天数据摊成 28 天。
